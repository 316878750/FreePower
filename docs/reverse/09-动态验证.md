> 实测日期：2026-11-11。环境：本机已装 AdsPower Global 8.9.23，Local API 50325。

## 1. 启动客户端时踩的坑（复现必看）

首次启动 `AdsPower Global.exe` 会**立即 exit code 0、不写日志**。原因是当前 shell 环境里有：

```
ELECTRON_RUN_AS_NODE=1
```

这个变量会让 Electron 以 node 模式运行，主进程根本不启动。
**清掉后正常**：`Remove-Item Env:ELECTRON_RUN_AS_NODE`，再启动，约 10 秒后 50325 监听。

## 3. `--extended-parameters` 解码（**静态报告的关键错误**）

### 3.1 不是标准 base64

实测按标准 base64 解码 → 得到二进制乱码（1052 字节，head `e7de0db8...`）。
真相：AdsPower 自己的 `encodeBase64` 是对 base64 **字符做替换表变换**：

```
标准字母表 STD    = ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789+/
自定义字母表 CUSTOM = hTy1bfRJz4nLPcBCO7WtmNIaGvVeul5Zo8kq32UxrYw_-0gsjp96SDFXQiEMKdHA
```

编码：`stdBase64` 的每个字符 → 用它在 STD 里的下标，去 CUSTOM 取同下标字符。
解码：反过来，再 `Buffer.from(s,'base64')`。

脚本：`tools/dyn/decode-ext2.js`

### 4.1.1 更正：`MediaDevices` 是**合成假设备名**，不是真实硬件

我最初把 `MediaDevices` 的三个 label 当成用户真实设备名（差点当成脱敏项）。读了 agent 代码后**推翻**：

v2.9.0.1 `setMediaDevices` 的实现（美化版约 12485 行附近）：

```js
var u = n[a % n.length] || n[0];
t.push({ kind: "audioinput",  label: u.input });
t.push({ kind: "videoinput",  label: "Integrated Camera (" + o + ":" + s + ")" });
t.push({ kind: "audiooutput", label: u.output });
```

- `n` 是内置的**候选池**（6 条 `input`/`output` 配对，全是 Realtek / Conexant / Synaptics 这类常见声卡名）；
- `a` 是哈希派生的数值 → `n[a % n.length]` 只是从池里挑一条；
- `o`/`s` 是 `charCodeAt` 累加取 hex 的首尾各 4 位 → 摄像头 label 形如 `Integrated Camera (5e02:75ee)`，**那串 VID:PID 是算出来的，不是枚举来的**。

**结论**：这些名字是 AdsPower 自己编的，与用户硬件无关。所以：
1. 不存在"泄露用户声卡名"的问题（我先前按真实硬件做了占位替换，属于保守处理，不影响结论）；
2. 这反而是**新的检测点**：`mediaDevices` 的摄像头 label 恒为 `Integrated Camera (<4hex>:<4hex>)` 且 hex 由字符串哈希派生，音频 label 只会是那 6 条之一 —— 真实机器几乎不可能正好长这样。
3. 复刻时按这条实现即可：**池 + 哈希派生**，不要枚举真实设备。

## 5. DynamicConfig 是否"换 IP 原地改写"（**重点，结论有修正**）

### 5.1 实测：空闲与重启都不改写

| 测试 | 结果 |
|---|---|
| 浏览器运行中空闲 45 秒 | mtime 不变、内容 hash 不变 |
| stop → start 一次 | **三个文件 mtime 全部不变、内容全部不变** |

重启后 `mtime_changed=false` 对 dynamic / static / cookies 全部成立。

原因在代码里（v2.8.9.2 偏移 431289）：写文件前先读旧文件算 md5，**内容一致就跳过写入**：

```js
be = read(ve); we = md5(be); ... we === Ae && (ye = false) ...
ye ? write(ve, encodeBase64(_e)) : skip
```

所以**"每次启动都重写、mtime 会变"的说法是错的**。mtime 只在内容真的变了才更新。

### 5.2 代码里确实存在运行时改写路径

`DynamicConfig` 有 3 个运行时写入点（v2.8.9.2）：

| 触发 | 偏移 | 写入内容 |
|---|---|---|
| agent 收到串 `UPDATE_IP_$$_<新IP>` | 445489 | `WebRTCAddress = 新IP`，并删 `DisableWebRTC` |
| 城市/国家变化且 `IS_REALTIME_TZ_GEO=true` | 463785 | `TimeZone = 重算值` |
| 经纬度变化且 `IS_REALTIME_TZ_GEO=true` | 465178 | `Geoposition = lat,lon,acc` |

发送方 `UPDATE_IP_$$_` 不在 agent 包内（全包仅 2 处，都是接收端），**在混淆的 `dist/main.js`（Electron 主进程）里**。

### 5.3 实测追查：消息通道找到了，但触发条件没满足

第二轮按 CEO 的要求换做法（不碰代理、不碰既有配置），结果如下。

#### 5.3.1 消息通道不是 IPC，是**页面的 console 输出**

v2.9.0.1 美化版约 8935 行：`initPageListen` 里挂的是 `page.on("console")`，然后对 `console` 文本做 `indexOf` 匹配：

```js
this.page.on("console", function (t) {
  e = t.text();
  if (e.indexOf("UPDATE_TIMEZONE_$$_") > -1) { ... this.updateTimezone(...) }
  if (e.indexOf("UPDATE_GEO_$$_") > -1)      { ... this.updateGeo(...) }
  if (["proxy","forward"].includes(this.webrtc)
      && "true" === process.env.IS_SUNFLOWER_BROWSER_CANVAS
      && e.indexOf("UPDATE_IP_$$_") > -1) {
    p = e.replace("UPDATE_IP_$$_","").trim();
    delete this.dynamicConfig.DisableWebRTC;
    this.dynamicConfig.WebRTCAddress = p;
    X(md5file, encodeBase64(JSON.stringify(this.dynamicConfig)));   // 重写文件
  }
  if (e === "disconnect") this.browser.disconnect();
});
```

**这是本次最有价值的结构性发现**：主进程不是通过 IPC 通知 agent，而是**在页面里 `console.log("UPDATE_IP_$$_<ip>")`**，由 agent 从 console 事件里捞。副作用是：**任何页面只要输出这段字符串，且条件满足，就能改写这个环境的 WebRTC 出口 IP 并删掉 `DisableWebRTC`**。这是一条实实在在的注入面。

（我已把 `console.log("disconnect")` 也记下来 —— 那段代码会把 agent 与浏览器断开连接。）

#### 5.3.2 为什么没能复现成功

先试了「新建一次性环境」，被账号上限挡住：

```
POST /api/v1/user/create
→ {"code":-1,"msg":"If the number of imported accounts exceeds the limit of 100, ..."}
```

本机账号已有 100 个环境（`tcoin_b1..b100`），**无法在不删用户数据的前提下新建**。所以只能退到既有环境上做**字节级可逆**的实验：

1. 备份 `DynamicConfig` 原始字节 + mtime（存 `8.9.23\dyn-backup\`）；
2. 起浏览器，用 CDP 往**所有 page target** 注入 console 指令；
3. 比对文件 md5；
4. `finally` 里停浏览器并**按原始字节还原**，校验 md5 一致。

做了三轮，全部没改写：

| 轮次 | 发送内容 | 目标页面 | 结果 |
|---|---|---|---|
| 1 | `UPDATE_IP_$$_203.0.113.77` | 第一个 page（`start.adspower.net`） | 无变化 |
| 2 | 同上 | **两个** page（`start.adspower.net` + `hey.xyz`） | 无变化 |
| 3 | TZ + GEO + IP 三条一起 | 两个 page | 无变化 |

每轮都确认 CDP 返回 `{"result":{"type":"string","value":"sent"}}`，即**消息确实执行了、只是没被处理**。
三次还原校验全部 `✅ md5 一致`，环境未被改动。

#### 5.3.3 卡在哪个条件上

`UPDATE_IP_$$_` 分支要同时满足 3 个条件：

| 条件 | 本机能否验证 | 说明 |
|---|---|---|
| `["proxy","forward"].includes(this.webrtc)` | 否 | 该环境的 webrtc 模式不是 proxy/forward（Local API 的 `user/list` 不返回 `fingerprint_config`，无法免启动读取） |
| `process.env.IS_SUNFLOWER_BROWSER_CANVAS === "true"` | 否 | agent 进程环境变量无法从外部读取 |
| 消息文本含 `UPDATE_IP_$$_` 且 IP 非空 | ✅ | 已满足 |

TZ/GEO 两条**本来就不写这个文件**（它们走 CDP 覆盖时区/经纬度），所以它们没变化不代表通道不通 —— 只有 IP 那条会落盘。

**结论（状态标记）：代码路径已确认、消息通道已定位到 `page.on("console")`，但运行时改写在本机条件下未能复现。** 报告 04 §3 的「C 通道运行时可变」保持"代码确认、未实测"。

**要真正钉死，需要满足其一**：
1. 账号腾出一个环境名额 → 新建 `webrtc=proxy` + `no_proxy` 的一次性环境，跑 `tools/dyn/test-update-ip.js`（脚本已就绪，会自动删环境）；
2. 授权临时把某个环境改成 `webrtc=proxy`（可逆，改回即复原）；
3. 抓一次真实的「换代理 IP」操作：主进程日志里会先出现 `[<id>]-update IP: {...}`，随后才是文件改写。

#### 5.3.4 顺带确认的启动期事实

主进程日志每次启动都有这两行（说明 IP 更新流程本身在跑）：

```
open - updatebrowserinfo update tz: America/Los_Angeles
open - [<profileId>]-update IP: {"fbccUserId":"<profileId>","proxyType":"other","country":"us",...}
```

配合 §5.1 的「内容不变就不写」，可以解释为什么每次启动 mtime 都不变：**流程跑了，但因 IP 没变而跳过了写入。**

### 8.1 重点抓手：`MediaDevices` 是合成设备名，VID:PID 是算出来的

这是本次唯一一个**能直接写成检测规则**的发现，单独拎出来。

#### 机制（v2.9.0.1 源码）

```js
var u = n[a % n.length] || n[0];
t.push({ kind: "audioinput",  label: u.input });
t.push({ kind: "videoinput",  label: "Integrated Camera (" + o + ":" + s + ")" });
t.push({ kind: "audiooutput", label: u.output });
```

- `n`：内置候选池，6 条 `input`/`output` 配对，全是 Realtek / Conexant / Synaptics 这类常见声卡名；
- `a`：哈希派生的整数 → `n[a % n.length]` 只是从池里**挑一条**；
- `o` / `s`：`charCodeAt` 累加后转 hex，取首 4 位与尾 4 位 → 拼成 `(<4hex>:<4hex>)`。

#### 为什么可作检测特征

| 真实机器 | AdsPower 环境 |
|---|---|
| USB VID 由厂商分配（`8086`/`0bda`/`046d`…），是**稳定的厂商前缀** | `(5e02:75ee)` 这种两头随机，**不代表任何厂商** |
| 摄像头 label 通常是厂商型号，如 `HD Webcam C270` | 恒为 `Integrated Camera (...)`，**型号永远是这两个词** |
| 音频 label 与系统实际驱动对应，逐机不同 | 只能落在**固定的 6 条池**里 |
| 多设备时 label 互不相同 | 同一池可能重复命中 |

**可落地的判据**：
1. `enumerateDevices()` 里 `videoinput` 的 `label` 匹配 `/^Integrated Camera \([0-9a-f]{4}:[0-9a-f]{4}\)$/` → 高度可疑；
2. 把那段 hex 对照真实 USB VID 数据库，查不到厂商 → 加分；
3. `audioinput` 的 label 落在那 6 条白名单内且**同时**满足第 1 条 → 基本可判定；
4. 需要 `getUserMedia` 授权后 label 才非空 —— 检测脚本要先申请权限，这一点要考虑用户拒绝授权的情况。

#### 复刻注意

**直接照抄这套合成逻辑是安全的**（它本身不暴露什么），但要知道：**它是可被指纹化的**。FreePower 若想做得更好，就该从真实设备枚举里挑，或者至少让 VID 取自一张真实厂商表，而不是哈希随机。

（最初我把这三个 label 当成用户真实硬件做了脱敏处理，读了源码才发现判断错了 —— 教训见 `REDACTION.md` §7。）
