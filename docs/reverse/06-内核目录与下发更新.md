`components` 这个目录名不是随便起的——代码里 `staticConfig.ComponentPreinstallPath = <cwd_global>\chrome_<ver>\components`（@29453），内核启动时把组件预置目录指到这里，避免在线拉组件。

### 签名机制【实】

`chrome.dll.sig` / `SunBrowser.exe.sig` 都是 **1430 字节的 DER 编码 PKCS#7（Authenticode）签名**，内容里可见 `US`、`Washi`（Washington）等 X.509 字段。不是简单 hash。

→ 含义：**AdsPower 只启动签名校验通过的内核**。这也解释了为什么 `update-patch` 存在——补丁必须重新签名。

## 3. 下发方式【实】

### 3.1 下载 URL 规则

从 `.zip.info` 里读出的真实 URL：

```
https://version.adspower.net/software/browsers/chrome/<YYYYMMDD>/SunBrowser-64-<大版本>-<YYYYMMDD>.zip
例：https://version.adspower.net/software/browsers/chrome/20240119/SunBrowser-64-118-20240119.zip
```

域名是 `version.adspower.net`（不是 `api-*`，内核走 CDN 不走业务 API）。

### 3.2 断点续传 manifest（`.zip.info`）【实】

每个 zip 旁边一个 `.zip.info`，是**分块下载的进度账本**：

```json
{
  "url": "https://version.adspower.net/software/browsers/chrome/20240119/SunBrowser-64-118-20240119.zip",
  "etag": "\"15C12971C1F7C0DCCB51D9B2C3A672A0-150\"",
  "fileName": "<下载时的绝对路径>",
  "contentLength": 156633360,
  "contentType": "application/zip",
  "blocks": [ {"start":0,"end":4194303}, {"start":4194304,"end":8388607}, ... ],
  "pointer": 38
}
```

- 块大小固定 **4 MB**（`4194304`），最后一块收尾对齐 `contentLength`。
- `pointer` = 已完成到第几块（上面这条已完成 38 块，共 38 块 → 下完了）。
- `etag` 用来判断远端文件有没有变。
- 验证：`.zip` 大小 189,853,554 与 `contentLength` 一致（是针对 131 那个包的；118 的包 156,633,360 对上表里 156.6 MB）。

→ **复刻要点**：内核下载必须支持**分块 + 续传 + etag 校验**，否则 300 MB 断一次就得重来。

### 3.3 保留策略：只留最近 5 个

代码里 `keepFilesNum = 5`（@1264724 agent_core、@1274043 rpa_plus），清理逻辑是**按 mtime 倒序取前 5，其余 `unlink`**。

实测：`.browser\` 里只剩 7 个 zip（118 / 119 / 124×2 / 126 / 128 / 131），而 `cwd_global\` 有 20 套已解压内核 → **zip 解压后被清掉，只留最近几个**；解压出来的目录不删。

### 3.4 版本键 `update_version_key`【实】

`chrome_142\update_version_key` = `20251218`（8 字节 ASCII）。
代码里大量按它做能力门控，例如：

```js
+updateVersionKey.substring(0,8) >= 20251126   // 多级代理需要的能力
+updateVersionKey.substring(0,8) >  20240815   // SecurePreferenceSync
+updateVersionKey.substring(0,8) >= 20231115   // 某些 darwin 行为
```

→ 这是**内核构建日期**，不是版本号。复刻时如果要做能力分级，得自己另设一个等价字段。

## 4. 版本选择逻辑

1. `fingerprint_config.browser_kernel_config = {version, type}`，`version` 缺省 `"ua_auto"`。
2. `"ua_auto"` 时由 **UA 串里的 Chrome 主版本**反推该用哪套内核（`getChromeVersion(ua)`，@5515 附近）。
3. 显式版本时直接用，`type` 必须是 `chrome` 或 `firefox`，且**版本必须在该 type 的合法集合内**（官方 `browser-kernel-config.md`）。
4. 目标内核不存在 → 触发下载，或被拒（`100015 BROWSER_DOWNING` / `100012 BROWSER_PATH_WRONG`）。

## 6. 给 FreePower 的建议

**不需要复刻 20 套内核。** 我们没有重编译 Chromium 的能力（也没有指纹模块可打进去），所以：

1. **MVP 用 CfT（Chrome for Testing）+ 本机 Chrome**，一到两个版本足够跑通。FreePower 已经在用本机 Chrome 156 验证，方向对。
2. **目录结构照抄**，因为这决定了 `/kernels` 接口的形状和用户的升级路径：
   ```
   kernels\chrome_<大版本>\<完整版本号>\chrome.exe
   kernels\chrome_<大版本>\chromedriver.exe
   ```
   `chromedriver` 跟着内核版本走、不共享——这条建议保留，能省掉大量版本不匹配的 bug。
3. **分块续传必须做**：300 MB 级别的包，断点续传 + etag 是必需项，不是优化项。可以直接照抄 `.zip.info` 的字段设计（`blocks[]` + `pointer`）。
4. **保留 5 个版本**这个策略可以照抄，简单有效。
5. **不要做 `.sig` 验签**：我们没有签名私钥，做不了；产品文案里别宣称"内核签名校验"。
6. `update_version_key`（构建日期）这个设计值得学：**用一个单调递增的日期键做能力门控**，比按版本号硬编码分支好维护。
