## ① 合并 Cookie 可撤销

### 问题

合并（并集）虽然「同名以现有为准、不覆盖登录态」，但它会**往环境里加 cookie**，而且用户是对着一批
环境批量操作的 —— 选错环境、拿错文件、点错确认，一次就污染几十个环境。之前**没有任何回退路径**
（`21-FreePower实现清单.md` §5 里 `undoMerge` 是零实现）。

### 做法

每次**真写**的合并，在写之前先把「这个环境合并前的 cookie 全集」落一份盘上的记录
（`src/store/cookie-undo.js`），撤销时把它写回去并逐条比对。

四条设计选择，都写清为什么：

1. **只保留最近一次**（一个环境一个文件，新合并覆盖旧记录）。不做无限历史：
   历史越久，「撤销」到底回到哪一刻就越说不清；用户真正需要的是「我刚才那一下合错了，退回去」。
   界面上明说这一点（批量菜单的 title、预览弹窗里都有）。
2. **落盘，不是记日志**。进程崩了、重启了，撤销还得能用 —— 日志读不回来。
3. **快照写不进去就不许合并**（fail-closed）。写不了回滚记录的合并就是一次不可回退的破坏性操作；
   宁可这一条合并失败并说明原因（`snapshot_failed`），也不做「先合了再说」。
4. **原子写**（`<id>.json.fp-tmp` → rename）。崩在写一半，盘上要么是上一份完整快照、
   要么是这一份完整的，不会出现半截 JSON 把撤销弄坏。

撤销本身：`POST /api/v2/browser-profile/batch/cookie/undo`（支持 `preview:true` 只算不写），
另有 `GET` 同一路径查「这些环境里哪几个有得撤」。撤销成功后**立刻删掉记录** ——
第二次撤销就该如实说「没有可撤销的合并」。

**B 层 `test/cookie-undo-kernel.test.mjs`（30 条，已进 `npm run smoke`，`npm run test:cookie-undo-kernel`）**

真内核（157.0.8103.78）、两个环境各自预置 cookie，然后：

- **合并 A+B → 撤销 → A 与 B 各自逐条 deepEqual 回到合并前**（比到 value：`sid=A-old` / `sid=B-old`）。
- 合并加进来的那条被撤销删掉（「回到合并前」就是这个意思）。
- 撤销预览只算不写（预览之后 `fromfile` 还在）。
- 第二次撤销 → `no_merge_to_undo`、`restored=0`，且**没动内核**。
- 连合并两次 → 撤销只回到**第二次合并前**（`one` 还在、`two` 被删）—— 这就是「只保留最近一次」。
- 合并后环境进回收站 → `in_recycle_bin` 且**保留**快照；彻底删除 → `not_found`，HTTP 200 不崩。
- 「还原（覆盖）」**不产生**撤销记录、`undo_available=false`（它的语义是「以文件为准」，不提供撤销）。

### 先红后绿（都实跑）

**红 1 · 快照存的是空集合而不是合并前的真实集合**（`routes.js` 里 `saveMergeSnapshot(p.id, existing, …)`
改成 `saveMergeSnapshot(p.id, [], …)`）：

```
✖ 撤销预览：A 会删掉 1 条（合并加进来的 fromfile）、写回 0 条  — {"d":3,"a":0,"u":0}
✖ **A 逐条 deepEqual 回到合并前**（含 value：sid=A-old）  — after:[]
✖ **B 逐条 deepEqual 回到合并前**（含 value：sid=B-old）  — after:[]
✖ 撤销报告里 deleted=1、written=0（说的是它真做的事）  — [[0,3],[0,3]]
✖ 第二次撤销**没动内核**：A 的集合还是合并前那份
✖ 撤销回到**第二次合并前**（one 还在、two 被删）
24 PASS / 6 FAIL
```

**这次红里有一条特别值得记**：「撤销真写：两个环境都 restored=true、verified=true」**仍然是绿的** ——
因为空集合写回去之后，比对的是「空 vs 空」，自己跟自己对上了。这正是
「只验证撤销流程跑通」会骗人的地方，也是为什么必须拿**合并前的真实集合**做 deepEqual。

**红 2 · 比对只看条数、不比 value**（`compareCookieSets` 里删掉 value 比较那一行）：

```
✖ **条数一样但值被换了 → 必须红**（只看条数会漏掉的就是这一类）  — {"ok":true,"changed":[],"totals":[3,3]}
30 PASS / 1 FAIL
```

**绿**：A 层 31 PASS / 0 FAIL、B 层 30 PASS / 0 FAIL（本轮实跑）。

### 界面

批量菜单新增一项「撤销上次合并 Cookie」。三步都不省：

1. 先查「这些环境里哪几个有得撤」（`GET`），没有就直接说「没有可撤销的合并」并列出原因，不让人点了确认才被告知；
2. 预览：会写回几条、**会删掉几条** —— 「合并之后新产生的 cookie 会被删掉」必须在确认前说清；
3. 真撤销，逐个报「逐条比对一致（真的回到合并前）」或差在哪几条。

「合并」的确认弹窗里也加了一句「合并之后可以撤销（**只保留最近一次**）」；
「还原（覆盖）」的弹窗里明写「**这一步不可撤销**（只有合并有撤销）」。

### 已知缺陷

1. **撤销的记录里存着 cookie 的 value**（登录凭据）。它落在 `<数据根>/cookie-undo/`，
   与 `freepower.db` 里 `cookie` 字段的信任边界一致（同一台机器、同一个用户）。
   接口与日志都**不打印 value**，但**这个目录本身是敏感文件** —— 备份/分享数据目录时要当凭据看待。
2. **撤销只对「最近一次合并」有效**，这是设计不是缺陷。要更早的状态只能靠 ② 的备份快照。
3. **撤销需要环境在跑**（cookie 在内核里，与合并同一条口径，不为撤销偷偷起内核）。
4. **「还原（覆盖）」没有撤销**：它的语义本来就是「以文件为准」，而且它自己已经走预览 + 确认两道。
   如果用户需要更宽的后悔药，那是 ② 的备份快照。
5. 快照文件在**环境被彻底删除后**仍然留在盘上（撤销时如实报 `not_found`）。
   目前没有清理机制 —— 要清理的话属于 ② 的备份管理，或在「彻底删除环境」时顺手删。
   **这一条是本版已知的小垃圾**，写在这里不藏。

## ④ 按天数删缓存

### 问题

环境一多，`data\profiles\` 就是磁盘黑洞：一个 userdata 十几到几百 MB（本机实测一个新环境刚启动一次就
**14.7 MB**）。用户想「把三个月没开过的环境的缓存清掉」，这件事**不可逆** —— 删掉的是 cache + cookie +
localStorage + 书签 + 登录态，删完下次启动是全新浏览器。

### 做法

**两阶段，不许合并成一步**：

1. `POST /api/v2/browser-profile/cache-cleanup/preview`（只读）→ 回「将删哪些、每个多大、在哪天开的、
   哪些不删以及为什么」（**这条不给 `profile_ids` 是合法的**：本意就是筛全部）；
2. `POST /api/v2/browser-profile/cache-cleanup` + `confirm_ids` → 真删，**实际删的 = 用户确认的 ∩ 现在的计划**；
   **不带 `confirm_ids` 一律拒**（详见下面第 3 条）。

四条设计选择，都写清为什么：

1. **天数只认 `profiles.last_launch_at`**（我们自己记的「最后启动时间」），**绝不拿文件 `mtime` 猜**。
   `mtime` 会被备份、复制、解压、杀毒软件改掉 —— 拿它判「多久没开」会删掉天天在用的环境。
   这一条有静态判据钉着：`cache-cleanup.js` 的**代码里**出现 `mtime` 就红（注释里解释为什么不用它，不算）。
2. **没有记录 = 判定不了 = 不删**（`keep.reason = 'unknown'`），并单独计数 `unknown_count` 让界面能说
   「N 个判定不了」。这是本版最容易被忽略的一条：`last_launch_at` 这个列一直存在，但**0.4.7 之前从来
   没人写过**，所以升级上来的老环境**全是 unknown**。第一次用会看到「一个都删不了」，这是对的，不是 bug。
3. **只删清单里那些，且真删必须带清单**。计划是「算」出来的，而用户点确认到服务端执行之间状态可能变
   （比如某个环境刚被启动）。两边都同意才删；确认之后变了的进 `kept_after_confirm` 如实报回来。

   **两条路由的语义是刻意不对称的**（这是 CEO 复验时抓出来的真漏洞，原来代码是「没带就等于全选」）：
   - `preview` **不给 `profile_ids` 是合法的** —— 它的本意就是「按天数把全部环境筛一遍」；
   - 真删 **不给 `confirm_ids` 一律拒**（`100002` + `field: 'confirm_ids'`，msg 让调用方先调 preview
     把 `profile_id` 列表带回来）。**空数组也算没带**。

   为什么真删不给清单不能当「全选」：API 是这个产品的一等公民（脚本、MCP 会批量跑），
   一个 `{days:30}` 的 POST 就能删掉几十个环境的登录态，而且它会**静默回 `code=0`** ——
   脚本根本不会以为出错。想删光就先把 preview 的清单原样带回来，那才叫「我看过并同意」。
4. **不删库记录**。环境还在（记录、代理、指纹配置都留着），只是浏览器里的东西没了；下次启动会重建一个
   干净的目录。要连记录一起删，那是回收站的「彻底删除」。

**代码里的 `markLaunched` 在启动成功之后才写**（`markStatus(id, 'running')` 之后、`return` 之前），
启动失败的那次不算「开过」—— 否则一个起不来的环境会永远删不掉。写失败只 WARN，不许因为一个时间戳起不来。

删的边界（实测确认）：`purgeProfileData` 是「先给整个 `<no>_<id8>` 改名成墓碑、再删墓碑」，
所以**父目录也一起没了**。这是刻意的 —— 父目录里只有 `userdata` 一个子目录，留着只会积一堆空壳。
判据钉住的是**没删到别人**：`profiles/` 这一层必须还在、兄弟环境一个字节没动。

### 已知缺陷

1. **没有定时任务**：用户要自己去点「先看看会删哪些」。路线图里这版没排调度，写在这里不藏。
2. **升级上来的老环境全是 `unknown`**：`last_launch_at` 在 0.4.7 之前没人写过。要等它们各自真启动一次

5. **UI 在回收站页**，靠页面滚动才能看到；环境特别多时预览表格会长（没有分页，只有勾选 + 折叠 keep 列表）。

## ② 本地备份快照（保留 5 个）+ 从备份恢复

### 问题

这一版前面那些不可逆动作（彻底删除、按天数删缓存、`clear_cache_after_closing`、合并/还原 Cookie、
换绑代理把登录态搞没）—— ① 只给了「最近一次合并」的撤销，**其余的全都没有回退路径**。
② 是那个兜底：把环境当前的样子整个存一份，随时能整份退回去。

### 一份快照里到底有什么（这条比代码重要）

```
<数据根>/snapshots/<profile_id>/<snap_id>/
  meta.json      —— 时间 / 原因 / 包含什么不含什么 / 文件数 / 字节数
  record.json    —— profiles 表这一行的**全部列**（含 cookie 字段、代理、指纹、UA…）
  userdata/      —— 内核数据目录的一份拷贝（**缓存目录除外**）
```

**包含**：环境记录的全部业务列；userdata 里的 Cookie/登录态、LocalStorage、IndexedDB、书签、历史、扩展设置。

**不包含**（两条都在界面上逐条列出来，`SNAPSHOT_SCOPE` 是唯一文案源）：

1. **可再生的缓存目录**：`Cache` / `Code Cache` / `GPUCache` / `DawnCache` / `ShaderCache` /
   `Service Worker` / `Blob_storage` / `Crashpad` / `BrowserMetrics` / `component_crx_cache` 等
   （名单是固定常量 `CACHE_DIR_NAMES`，不读环境变量、不按大小猜）。理由：浏览器能自己重建，
   存进去只会让一份快照从几 MB 涨到几百 MB，把「保留 5 个」变成占几十 GB 的摆设。
   **实测**：同一个真环境，userdata 14,766,439 B → 快照 2,571,441 B（B 层读数）。
2. **内核本体**（几百 MB 的 Chrome）。内核按版本单独下载，恢复时不涉及。

### 做法

六条设计纪律：

1. **保留 5 个**（`KEEP_SNAPSHOTS = 5`，每个环境各 5 个）。第 6 份进来时最旧那份被挤掉，
   **并且目录真的从磁盘消失**（`rmSync` 之后复查 `existsSync`，不是只从索引里删）。
   挤不掉（被占用）时**照样保留新快照**，但如实报 `removed:false`，界面说「有 N 份没删掉，暂时超过上限」——
   「因为删不掉旧的就不给备份」比「暂时多占一份」危险得多。
2. **恢复是破坏性的，所以恢复前自动给当前状态留一份**（`reason: 'before_restore'`）。
   **留不下来就拒绝恢复**（`before_snapshot_failed`）—— 否则恢复本身就成了新的丢数据入口。
3. **换目录走「改名 → 拷贝 → 删墓碑」**：拷贝失败就把原名改回来，一个字节都没变
   （与 `purge-data.js` 同一条纪律）。
4. **恢复后逐列核对**：核对范围是**快照里的全部业务列**，不是「刚写了哪些列」——
   否则「某一列悄悄没写」会自己跟自己对上（① 那条「空集合对空集合也是绿的」的教训）。
   不一致就如实报 `verified:false` + 哪几列不一样。
   **`verified` 必须同时覆盖数据层**：快照说包含 userdata，就必须真换上了（`userdata.replaced === true`）
   才允许 `verified:true`。只核对记录列 = 数据层一点没覆盖，「记录回到快照、登录态还是恢复前的样子」
   也会是 `verified:true` + `diff:{}`（这是 ② 第一次提交里的真实缺口，已修）。
5. **正在恢复的那份快照不许被自己的「恢复前」快照挤掉**。
   恢复的第 1 步会拍一份 `before_restore`，而拍照会触发轮转（超 5 份真删目录）。池子满 5 份时
   恢复**最旧那份**，新拍的第 6 份本来会把最旧那份删掉 —— 删的正是正在恢复的那份，于是
   userdata 找不到、静默跳过换目录，接口却回 `restored:true` + `verified:true`（**半恢复报成功**，
   而且目标快照被自己挤掉，想重试都没有了）。所以 `takeSnapshot` 收 `protect: [snapId]`，
   轮转跳过它、改删更旧的一份（总数照样回到 5，只是死的不是被保护那份）。
6. **快照声称有 userdata 就必须真有**：`meta.includes.userdata === true` 而盘上那份 `userdata/`
   不存在或为空 → **硬失败**（`snapshot_userdata_missing`），并且在**动任何东西之前**就失败
   （验数据层那一步排在拍 `before_restore` 之前，所以失败时连快照池子都没变）。
   同时把「快照里本来就没数据」这种正常情况和它分开：前者 `userdata.mode: 'not_in_snapshot'`，
   后者是失败。两种都 `replaced:false` 会让人分不清是「没恢复」还是「没得恢复」。

**在环境跑着的时候拍快照**（允许，但必须如实标记）：

拷的是活着的 userdata —— `Cookies` 是 WAL 模式的 SQLite，拷到一半可能是不一致的副本，
恢复回去可能「登录态少几条」或者 Chrome 打不开那份库。所以不禁止（边跑边备份是合理需求），
但 `meta.taken_while_running` 如实记下来：列表那一行带可见文字「运行时拍摄 · 数据可能不完整」，
恢复弹窗再提示一次，接口 `create` / `restore` 都回这个字段。**不许让人以为它跟别的一样可靠。**

**恢复哪些列、不恢复哪些列**（刻意的）：全部业务列都恢复；下面这些**保留现状**——
`id` / `profile_no`（环境身份）、`created_at`、`updated_at`（改成现在）、`status`（一律回 `idle`）、
`deleted_at` / `archived_at`（**不恢复**：否则「恢复一份归档时拍的快照」会让环境突然从主列表消失，
用户会以为环境被弄丢了）。

**接口**（五条，前四条全都要显式给 `profile_id`；purge-preview 可给 `all: true`）：

| 路由 | 语义 |
|---|---|
| `GET /snapshot/list` | 列表 + 占用 + `keep` + `scope`（含/不含什么，界面直接渲染） |
| `POST /snapshot/create` | 拍一份（`reason` 只认 `manual` / `before_restore` / `on_close`，别的拒）；**允许在跑的时候拍**，但 meta 记 `taken_while_running` 并回给调用方 |
| `POST /snapshot/restore` | **必须 `confirm: true`**（缺了拒，`100002` + `field: 'confirm'`）；在跑的环境直接拒；回 `verified` / `verified_record` / `verified_data` / `evicted` / `taken_while_running` |
| `POST /snapshot/delete` | 删一份 |
| `POST /snapshot/purge-preview` | **只读**：彻底删除前报「会连 N 份备份一起删（占 X MB）」，`{total_count, total_bytes, items}`，一个字节都不动 |

### 彻底删除时清掉旁挂数据（快照 + 撤销记录）

**问题**：环境记录从库里删掉之后，`restoreSnapshot` 需要 `profile` 记录 —— 没有任何入口能恢复
这个环境的快照。它们**看着像备份、实际永远用不上**，比没有备份更坏。① 的 `cookie-undo/<id>.json`
同一处顺手清（那条确实只是小垃圾）。

**做法**：

1. **只有彻底删除才清**。软删除（进回收站）和归档**一律不碰** —— 用户一放回收站备份就没了，
   那比不清更糟。所以清理挂在 `recycle-bin/purge` 里、并且只在 `purgeProfiles` **真的删掉了记录**
   之后调（`if (r.purged.includes(target.id))` 门控）。「盘删不掉所以不删库」那条分支里记录没删，
   快照也不清。
2. **删盘走「先改名再删」**（与 `purge-data.js` 同一条纪律）：直接 `rmSync(recursive)` 是先删内容
   再删目录，目录被占住时会内容删光了才报错 —— 报的和做的正好相反。改名失败 = 一个字节都没动。
3. **删不掉不许让整个删除失败**：环境照删，`snapshots_kept` 如实报，`artifacts` 里点名到
   profile_id 和原因。改名成功但墓碑删不掉时报 `snapshots_detached_path`（环境侧已经够不着了，
   但磁盘没腾出来）。
4. **界面必须提前说**：彻底删除的确认框里先调 `POST /snapshot/purge-preview`（**只读**，一个字节
   不动）拿到份数与占用，写明「会一并删掉这个环境的 N 份备份快照（占 X MB）……环境记录删掉之后
   这些快照就再也恢复不了了」。清空回收站的确认框同理（`all:true` 汇总全部）。

**接口**：

| 路由 | 语义 |
|---|---|
| `POST /snapshot/purge-preview` | **只读**预览：`{total_count, total_bytes, items:[{profile_id, count, bytes}]}`，入参 `profile_id`（数组/单个）或 `all:true` |
| `POST /recycle-bin/purge`（改） | 响应新增 `snapshots_removed` / `snapshots_kept` / `snapshots_freed_bytes` / `undo_removed` / `artifacts[]` |

**判据**（A 层组 11b 共 18 条 + 5 条静态，B 层组 9 共 6 条）：

- 软删除（走**真实 HTTP 软删除路由**）→ 2 份快照仍在；归档（真实批量归档路由）→ 仍在；
- 彻底删除 → 快照目录**真从磁盘消失**、`cookie-undo/<id>.json` 也没了、响应报 `snapshots_removed:3` + `undo_removed:1`；
- `purge-preview` 报出 3 份 + 字节数，且**没删任何东西**；
- **快照目录被真占用**（子进程 `cwd` 设在快照目录里 → Windows 下 rename EBUSY）→ 环境**照样删掉**、
  `snapshots_kept:2` 如实报、目录还在盘上、`artifacts` 点名；

- 静态：清理函数在 purge 块里、被 `r.purged.includes(target.id)` 门控、**软删除路径里一个都不许有**、

### 已知缺陷

1. **快照不加密**。`record.json` 与 `userdata/Cookies` 里都有登录凭据，落在数据目录下，
   与 `freepower.db` 同一信任边界（同一台机器、同一个用户）。接口与日志**不打印 cookie 值**，
   但**这个目录本身是敏感文件** —— 备份/分享数据目录时要当凭据看待。
2. **只救「环境被改坏 / 数据被误删」，不救硬盘坏**：快照和库在同一块盘上。整盘坏了要靠系统备份。
3. **恢复要环境先停止**：在跑的时候只拒不做（内核占着 userdata，覆盖只会半途失败）。
4. **5 份是硬上限、不分来源**：手动拍的、恢复前自动留的、将来关闭时自动拍的，共用一个 5 份的池子。
   所以「恢复前自动留的那份」也会挤掉一份更早的手动快照 —— 界面上按时间排，用户看得见挤掉了谁。
5. **快照是整份拷贝，没有增量**：userdata 大的环境（几十 MB）拍一次就占那么多，
   5 份最多几百 MB。没有做去重/压缩（本仓库不新增 npm 依赖，zip 只实现了「解包」）。
6. **没有定时/离线快照**：只在用户点、或关环境时拍（关环境自动备份由 ③ 提供，**默认关**，见 §③）。
   没有「每天凌晨自动备份」这种调度器 —— 那要常驻进程，本版是随主程序起的本地服务。
7. ~~环境被彻底删除后，它的快照目录仍然留在盘上~~（**已处理**，见下面「彻底删除时清掉旁挂数据」）。
   原来的定性是「小垃圾」，这个定性是错的：它不是占地方，是**够不着** —— 环境记录从库里删掉之后
   `restoreSnapshot` 需要 profile 记录，没有任何入口能恢复这些快照，**看着像备份、实际永远用不上**，
   比没有备份更坏。而且量不小（一个环境 5 份、删 20 个环境就是几百 MB 到 GB 级，界面一个字节都看不到），
   ③ 的自动备份会让池子长期满 5 份、更严重。
8. **运行中拍的快照数据可能不完整**：允许边跑边备份（用户需求），但那时拷的是活着的 userdata，
   `Cookies` 是 WAL 模式的 SQLite，拷到一半可能不一致。`meta.taken_while_running` 记下来了、
   界面也打了标记，但**没有做一致性快照**（真要一致得先停内核，或者用 SQLite 的 backup API
   逐库拷 —— 本版没做）。标了标记的那份，恢复后登录态可能少几条。
9. ~~池子满 5 份时恢复最旧那份会半恢复~~（`c0633cc` 的真实缺陷，**已修**）：
   恢复前的自动快照会触发轮转，把正在恢复的那份挤掉，于是 userdata 静默不恢复、接口却回
   `restored:true` + `verified:true`。现在 `protect: [snapId]` 保住目标、数据层缺失硬失败、
   `verified` 覆盖数据。判据：A 组 8/9 + B 组 8。**记在这里是因为「已修」也要留痕** ——
   这类缺陷的特征是「所有绿读数都绿，只有真登录态没了」，下次改动这块要重跑那两组。
10. **恢复会挤掉一份别的快照**：池子满时恢复，恢复前自动留的那份会让**另一份更旧的**被挤掉
    （目标快照本身受保护）。接口 `restore` 回 `evicted`、界面 toast 会说「顺带挤掉了 N 份更旧的快照」，
    但**用户没法选让谁死** —— 要保住某一份，先手动删掉别的、或把那份单独恢复一次再删。

## ③ 关闭环境时自动备份（可关，默认关）

### 问题

② 的快照只有用户**主动点**「现在备份一份」才有。真实事故的形态不是「用户点了备份但备份坏了」，
而是：开环境干完活、关掉，第二天再开发现登录态没了（站点过期、或 `clear_cache_after_closing` 把目录清了），
而**昨晚关的时候数据还是好的，只是没人去点那个按钮**。自动备份就是把「该点没点」这件事补上。

### 为什么默认关（产品决策，不是实现细节）

1. 这个开关会让磁盘**持续增长**：每个环境 5 份，每份是真 userdata 的拷贝（实测 14.7 MB → 2.5 MB，
   真实环境带 LocalStorage/IndexedDB 只会更大），几十个环境就是几百 MB 到 GB 级。
2. **替用户决定占磁盘是不可接受的**。所以：没存过 → 关；库里存了读不懂的脏值（如 `yes-please`）→
   也当关，并且 `broken:true` 如实告诉界面「存坏了」。
3. 关着的时候**连「上次自动备份」状态都不写** —— 否则界面会显示一条从没发生过的记录，
   用户会以为「它在帮我备份」。

### 做法

1. **开关存库里**（`meta` 表，键 `snapshot_on_close`），不存 localStorage：备份是**服务端**在
   `manager.stopProfile` 里做的，浏览器 localStorage 服务端读不到（和 `sync_defaults` 同一个理由）。
   键名不许改，改名等于把用户的选择丢掉。
2. `manager.autoSnapshotOnClose(profileId)` 三段：
   - **关** → `{created:false, reason:'disabled'}`，连状态都不记；
   - **开** → `takeSnapshot(profile, {reason:'on_close', running:false})`。
     `running:false` 是实情（内核刚退出、数据是静的），所以这一份**不算「运行中拍摄」**，
     不带那条「数据可能不完整」的标记 —— 与 ② 的 `taken_while_running` 区分开；
   - **失败** → 只记一行日志 `snapshot_on_close - fail - <reason>` + 记一次状态；
     **异常全部吃掉**（`reason:'exception'`），一个都不许冒泡。
3. **在 `stopProfile` 里的位置**：`markStatus(idle)` 之后、`scheduleCachePurgeOnClose` **之前**，
   外面再套一层 try。顺序不能反 —— 反了就是「等 2 秒缓存目录被删空，再去备份那个空目录」。
   `stopProfile` 的返回值新增 `snapshot_on_close`（`created` / `reason` / `snapshot` / `evicted`）。
4. **刚拍的那份必须受保护**：`takeSnapshot` 里 `rotate` 的 `protect` 追加本次 `snapId`。
   不追加的话，池子里全是恢复点时，按「恢复点最后淘汰」的规则，第一个被淘汰的正是**刚拍好的这份**
   —— 备份白做，而且返回 `created:true`，看起来成功了。
5. **淘汰顺序按「这份备份有多有用」，不按时间**（三档）：
   空壳 `before_restore`（1，最先死）→ 普通快照（2）→ 带 userdata 的 `before_restore`（3，最后死）。
   理由是真实踩到的：数据被删掉后又恢复了一次，那次拍的 `before_restore` 没有 userdata，
   只按「恢复点最后动」的话，这个空壳会长期占名额、把一份完整备份挤掉。
   `evicted` 每条带 `restore_point` 与 `has_userdata`，界面据此说清这次动的是哪种。
6. **路由**：
   - `POST /api/v2/settings/snapshot-on-close`：缺 `enabled` → `100002` + `field:'enabled'`；
     非布尔同样拒（不猜用户意图 —— 这是会占磁盘的开关）；
   - `GET /api/v2/settings` 新增 `snapshot_on_close` / `_saved` / `_broken` / `_state`；
   - `GET /api/v2/browser-profile/snapshot/list` 新增 `on_close: {enabled, saved, broken, last}`，
     `last` 是**这个环境**上一次自动备份的结果（不是全局最后一条）。
7. **库结构没动**：只用 `meta` 表，不新增表/列（`schema.sql` 与 0.4.6 逐字节相同）。

1. **开关是全局的，不是按环境**：用户可能只想给几个重要环境开。按环境开要加一列（本版不动库结构），

5. **备份是同步拷贝**：userdata 大的环境会让「关闭」多花几百毫秒（实测 14.7 MB → 2.5 MB 那份

6. **只在「正常停止」时备份**：进程崩了、被任务管理器杀掉、主程序被强杀 —— 这些路径不经过
   `stopProfile`，**不会**自动备份。这也正是「数据丢了」最常发生的时候，本版救不了。

## 0.4.7.1 · 修 P0：升级 0.4.7 后所有环境都打不开

### 问题（用户看到的那一句）

```
启动失败：start failed: client_hints.ua_full_version: UA 报 Chrome/133 但 ua_full_version=157.0.8103.78
```

用户 50 个未删除环境，拿他库的副本走产品自己的 `getProfile` + `checkProfile`：**50/50 全被这一条拦住**。
不是个别环境，是全部 —— 0.4.7 在他机器上完全不可用。

### 为什么会这样（成因链，探针实测，不是看代码猜的）

1. **记录是 0.4.4 时代建的**：`ua` 是导入时带进来的 `Chrome/133.0.6943.127`（AdsPower 导出的
   环境就带那一版 UA），而 `client_hints` 是**建环境那一刻按本机内核**填的
   （`src/fingerprint/generate.js` 用 `kernel.full_version`）。两者从此不是一版。
2. **0.4.7 的读路径把这件事放大了**：`client_hints` 缺失时按**本机内核**填默认值
   （`src/store/db.js` 的 `mapLegacyPayload` / `generateFingerprint`），UA 一个字节不动 ——
   于是记录**一读出来就自相矛盾**，哪怕它原来只是「没写」。
3. **0.4.6 把这条升级成了硬冲突**（`packages/profile/src/validate.js` 第 3 条）：
   `checkProfile.ok === false` → `startProfile` 在校验那一步就 throw。
4. **启动后的那次对齐永远轮不到**：`alignProfileToKernel` 要拿到 `Browser.getVersion` 才能跑，
   而它排在 `checkProfile` 之后 —— 校验先拦，内核都没起，跟版逻辑根本没机会执行。
   这就是「死胡同」：越自洽的跟版设计，越到不了。
5. **新建/导入也一样**：`createProfile` 先 `generateFingerprint({kernel})` 给出内核版 hints，
   再被导入文件里的 `ua`（133）覆盖 → **落库即矛盾**。所以不只是老数据，新导入也会踩。

### 修法（四件，都在这一版）

**1）读路径的默认值不许造矛盾**（`src/fingerprint/hints.js` 新增，`src/store/profiles.js` 的 `toApi` 调用）

三条规则，按顺序，前一条命中就不走后面：

| 情况 | 做法 |
|---|---|
| hints 有完整 `ua_full_version`，且与 UA 的 `Chrome/<major>` 矛盾 | **UA 为准**，把版本段对齐到 `<major>.0.0.0`；`brands` / `fullVersionList` 的版本段一起对齐（`Not_A Brand` 不动）；**`platform` 一个字节都不动** |
| hints 没有完整版本（或整份缺失） | UA 能解析出 `Chrome/<major>` → **用那个 major 派生**（`<major>.0.0.0`、平台三件套从 UA 推），**不许用本机内核版本** |
| UA 缺失 / 解析不出 Chrome 版本 | 才回落到本机内核版本（此时 UA 没声明版本，怎么都对得上） |

**读路径零写入**：`withClientHints` 返回新对象，不改入参、不写库。判据里连读 3 次后比对
库里那一行的全部列，逐字节相同 —— 读操作顺手「修好」用户数据等于把只读变成迁移，出了问题没法回退。

**2）不要再有死胡同：启动前预对齐**（`src/runtime/manager.js`）

`checkProfile` 红了以后，**先看红的是不是只剩「UA 版本 vs UA-CH 版本」这一种**：

- 只剩这一种 → 用 `src/kernel/version.js` 的 `alignProfileToKernel`（**同一个实现**，
  不在 `hints.js` 里另写一份）按本机内核对齐一次，**对齐后必须重查 `ok === true` 才采用**，
  记一行日志（`UA 预对齐`）+ 启动响应里一条 soft 告警 `ua_realign_precheck`；
- 还有别的硬冲突（`webgl="2"` 却没有 vendor/renderer、UA 是 Windows 但 `platform=MacIntel` 等）
  → **一个字节都不动，照旧阻断**。

预对齐**不落库**：它只是「这一轮拿来启动」的临时视图。落库只走启动后那次
（以 `Browser.getVersion` 的真值为准，目录名/注册表给的版本只是猜）。

**3）导入要提前说**（`src/store/transfer.js` / `src/api/routes.js` / 界面）

导入结果里逐条带 `ua_notice`，汇总带 `ua_aligned` 计数和一句人话：

> N 个环境的 UA 是 Chrome/133，本机只装了 157 内核；首次打开会按内核对齐 UA

界面在导入汇总的 toast 里显示（warn 色），并进「导入结果」清单 ——
用户会截图/复制那段去核对，只弹一个会消失的 toast 是不够的。
分批导入（`.txt`）按批累加，不会因为分 3 批就把这件事拆散报或干脆不报。

**4）保存侧同样不许写进矛盾对**（`src/store/profiles.js`）

`createProfile` / `updateProfile` 落库前都过一遍 `reconcileForWrite`：**UA 是身份，hints 是派生的元数据**，
有可解析的 UA 大版本就按它对齐 hints 版本段；UA 解析不出才保留调用方给的 hints。
所以「编辑页只改了 UA」不会留下一个旧版本的 UA-CH，「导入文件里 UA 133 + 我们默认 hints 157」
也不会存进一个矛盾对 —— 不许「存进去了、打开才报错」。

### 行为说明（**要写进升级说明**）

- 这些环境的 UA **首次打开会被对齐到本机内核（157）**。这是产品**既有的跟版策略**
  （`alignProfileToKernel`，0.4.x 起每次启动都会把 UA / UA-CH / `kernel_version` 拉到真实内核版本，
  并落库），**不是 0.4.7.1 新加的行为**。这一版新加的只是「对齐之前不再被校验挡住」。
- 对齐会**落库**（`ua`、`client_hints.ua_full_version`、`kernel_version` 一起变成 157），
  下次启动不再对齐；环境日志里有一行 `UA 跟版`。
- **读路径不改库**：在你的环境被打开之前，库里的老记录仍是原样（界面上看到的是自洽的读视图）。
- 想保留 133 的 UA 也可以：把 `client_hints.ua_full_version` 一起改成 133 那一版，
  或者用 `FREEPOWER_UA_AUTOALIGN=0` 关掉启动后的跟版（那样 UA 会一直是 133，
  但内核是真 157 —— 这就是「UA 与内核不一致」，只影响指纹一致性，不影响能不能打开）。

### 已知缺陷

1. **读视图里的 hints 版本段是 `<major>.0.0.0`**，不是 UA 字符串里的完整 `133.0.6943.127` ——
   老记录里没有那个完整号可抄（hints 整份缺失），只能按大版本造一个自洽的。
   真正启动时以 `Browser.getVersion` 为准并落库，所以这只影响「打开之前界面上看到的那一版」。
2. **预对齐用的是 `findChrome()` 的版本**（目录名 / 注册表 / 上次实测的缓存），不是
   `Browser.getVersion` 的真值 —— 真值在启动后那次对齐里再修一遍，最坏情况是「多对齐一次」。
3. **只对齐版本号，不对齐平台**：UA 说 Windows 但 `platform=MacIntel` 这种仍然阻断（故意的，
   平台是另一条独立的一致性要求，放宽了等于把指纹矛盾从一条挪到另一条）。
4. **50/50 验收依赖 CEO 本机的那份副本**；副本不在时那条判据是 SKIP，不会假装通过。
5. **读路径给的是自洽视图，不是修复数据**：库里的老记录在被打开（跟版落库）之前仍是矛盾对。
   好处是可回退、读不写；代价是「别的东西绕过 `toApi` 直接读库」时仍会看到矛盾对
   （`checkProfile` 仍会如实报出来，这正是判据里「原始记录还是矛盾的」那一条）。
6. **导入提示只覆盖「UA 大版本 ≠ `kernel_version` 大版本」**：UA 与 hints 内部矛盾但大版本
   恰好一致的记录不会提示（这种记录读出来本来就自洽，不构成风险）。
7. **`getHighEntropyValues(['uaFullVersion'])` 这一口径保不住 133**（CEO 2026-11-16 探针实测，
   **只记录，本版不改**）：真内核上 `Emulation.setUserAgentOverride` 的 `brands` / `fullVersionList`
   **都能覆写**（实测 133 生效），但**已废弃的 `uaFullVersion` 永远返回真实内核版本**
   （实测 `157.0.8103.78`；手动再覆写一次也一样）。所以「UA 报 133、内核 157」这种组合
   在 `getHighEntropyValues(['uaFullVersion'])` 上是能被看出破绽的。
   要真正保住 133 只有两条路：装 133 内核（排进 0.4.9 的「环境级内核版本」），
   或在注入层 patch 这个已废弃的 API。**本版不改**：默认跟版策略下 UA 会被拉到内核版本，两边本来就一致。

## 0.4.7.2 · UA 跟版默认关 + UA-CH 逐项忠实（2026-11-16 用户拍板）

0.4.7.1 修的是「升级 0.4.7 后所有环境都打不开」。这一版修的是**修法的方向错了**：
0.4.7.1 的兜底是「按本机内核把 UA 对齐成 157」，可用户要的是**保住他存好的 133**。

### 为什么翻默认（用户的证据，不是口味）

- 对手的 `ua` 与 `client_hints` 是**两个各自可配的字段**（逆向 `02-指纹字段表.md:168-169`，
  `client_hints` → `staticConfig.UserAgentMetadata`）。内核换了，它不会去改用户存好的 UA。
- 用户的 SunBrowser 也是 Chrome 157（20261109），可他 50 个环境的 UA 就是 133 ——
  在 AdsPower 里能正常跑。我们「首次打开就写成 157」等于**把他的指纹改掉了**，而且不可逆
  （原值没有第二份）。
- 所以跟版从「默认行为」降级成「显式开关」，默认关。

### 三件事

1. **跟版默认关**（`src/config.js` 的 `UA_AUTOALIGN` 默认 false；设置页「UA 跟随内核版本升级」
   默认关，存库 `meta.ua_autoalign`）。关着时**任何路径都不改写** `ua` / `client_hints` /
   `kernel_version`：启动后那次 `applyProfileFields(id, aligned.patch)` 不执行，
   **启动前那次 `preAlignForLaunch` 也不执行**（它不落库，但会改「这一轮呈现的指纹」，
   同样属于改写）。关着时「UA 133 / 内核 157」只记一行日志，**不往启动响应里塞告警**
   （否则 50 个环境每次启动都弹一条）。
2. **UA-CH 逐项忠实**：
   - `uaFullVersion` 内核永远不认 —— 真内核实测（157.0.8103.78）：`Emulation.setUserAgentOverride`
     的 `userAgentMetadata` 里 `brands` / `fullVersionList` / `platformVersion` / `architecture` /
     `bitness` / `model` / `wow64` 都生效，唯独 `getHighEntropyValues(['uaFullVersion'])`
     永远返回真实内核版本（传 133 读回 157.0.8103.78，同一会话里手动再覆写一次 + reload 也一样）。
     这一项只能在注入层 patch：`src/kernel/inject.js` 新增 `patchUaData()`，
     `evaluateOnNewDocument` + `native()` 伪装 + 「toString 里含 native code」前置判断（防重复注入）。
   - **`platformVersion` 漏的真实原因不是 CDP**：主帧 / 新标签页 / 同 target 的第二个会话都拿到了
     profile 的值（实测 10.0.0）。漏的是**跨站子帧**——它是个独立 target（OOPIF），
     而 `handleNonPageTarget` 对 `type === 'iframe'` 一直只是「计数 + 放行」。实测（未修时）：
     父帧 `133 / 10.0.0`，同一页里的跨站 iframe 读到 `Chrome/157`、`platformVersion 19.0.0`、
     真 `uaFullVersion`、`brands` 还是宿主那套（`Not-A.Brand;v=99`）。
     修法：对 iframe target 发一次 **CDP 原生** `Emulation.setUserAgentOverride`（不注入 JS，
     没有新的痕迹面），`waitForDebuggerOnStart` 保证覆写先于子帧首文档。注入层那一套
     （canvas / audio / 字体…）仍然不覆盖子帧，照旧写在已知限制里。
   - 同时把**整套** UA-CH 一起钉住（「值不对才补」）：CDP 落地时一个字段都不改；
     万一哪条路径没落地，页面读到的也是 profile 这一套，不会出现「brands 157 + uaFullVersion 133」
     这种更显眼的半套状态。

### 已知限制（本版没解决的，照旧如实写）

1. **子帧只覆盖 UA / UA-CH**：跨站 iframe 里的 canvas / audio / 字体 / WebGL 仍是宿主真值
   （注入层不覆盖 OOPIF，P2 起就写在限制里）。要根治得给每个 iframe target 也挂
   `Page.addScriptToEvaluateOnNewDocument`，风险和收益要在 0.4.8/0.4.9 单独评估。
2. **`uaFullVersion` 是 JS 层补的**：`Function.prototype.toString` 已伪装成 native（与
   `hidden_notification` 同一套），但「跨 realm 取原生 toString 再比对」这类检测仍可识别 ——
   与 canvas/audio 那些注入项同级的限制。真要内核级只有装 133 内核（0.4.9「环境级内核版本」）。
3. **UA 里的完整版本与 hints 的版本段可能不同**：导入的老环境 UA 是 `133.0.6943.127`，
   而 hints 的 `ua_full_version` 是打码值 `133.0.0.0`（0.4.7.1 的读路径派生规则，见上文）。
   大版本一致、`brands` 一致，但「UA 四段 vs UA-CH 四段」严格比对时能看出后三段是打码值。
   这一条**本版没改**：改派生规则会动到 0.4.7.1 已验收的 50/50 行为。

## 0.4.7.2 第二版 · OOPIF 的 `uaFullVersion` 与「版本号做实」（2026-11-16 CEO 复验打回）

上一节那一版**有一条是假的**：跨站子帧（OOPIF）里的 `uaFullVersion` 仍是 `157.0.8103.78`。
CEO 用自己的探针打出来的读数：

```
父帧     UA=133 brands=133 fvl=133 uaFullVersion=133.0.0.0 platformVersion=10.0.0   PASS
新标签页 同上                                                                        PASS
跨站子帧 UA=133 brands=133 platformVersion=10.0.0 uaFullVersion=157.0.8103.78        FAIL
```

### 为什么会漏（不是「没写」，是「写了但不生效」）

第一版对 iframe target 只发了一条 **CDP 原生** `Emulation.setUserAgentOverride`，理由是
「CDP 覆写没有新的痕迹面」。可 `uaFullVersion` 恰恰是 CDP **永远不认**的那一项
（上一节已实测）—— 子帧里没有注入层，就必然读到宿主真值。**两条通道本来就是一对，
只发一条等于把已知会漏的那一项留给子帧。**

### 修法一：子帧挂一份「只做 UA-CH」的最小脚本

- `src/kernel/inject.js` 把共用核心拆成三段（`CORE_PRELUDE` / `CORE_NOISE` / `CORE_UA_CH`），
  `CORE = 三段拼起来`，**page / worker 两侧的注入源字节不变**（判据里逐字节比对过）。
  拆开只为让子帧能只装 `CORE_PRELUDE + CORE_UA_CH`：
  新增 `buildUaChOnlySource()`（约 9.2 KB，不含任何噪点/字体/WebGL/媒体设备代码）。
- 为什么连 `Function.prototype.toString` 接管也带上：`patchUaData` 用 `native()` 登记包装函数，
  没有那一层，子帧里 `getHighEntropyValues.toString()` 会吐出我们的真源码 —— 比不补更显眼。
- `src/runtime/manager.js` 的 iframe 分支：`Emulation.setUserAgentOverride` **和**
  `Page.addScriptToEvaluateOnNewDocument` 两件事都发，**都落地才 `runIfWaitingForDebugger`**
  （每条各自记账，`IFRAME_ARM_TIMEOUT_MS = 1500` 兜底，超时也放行 —— 停住的子帧 = 白屏）。

**踩到的第二个坑（这才是真正让它不生效的原因）**：
`Page.addScriptToEvaluateOnNewDocument` 只对**下一个**文档生效，而子帧被
`waitForDebuggerOnStart` 停住时，**它的首个文档已经建好了**。第一版补上脚本后探针读数是：

```
attach 事件：{"type":"iframe","waiting":true}
workerStats：iframes=1 iframes_ua=1 iframes_ua_ch=1 iframes_ua_ch_failed=0   ← 注册成功了
oopif read ：ua=Chrome/133 brands=133 platformVersion=10.0.0 uaFullVersion=157.0.8103.78
```

注册成功、CDP 覆写生效、唯独 `uaFullVersion` 没变 —— 因为脚本没在当前文档里跑过。
修法是加 **`runImmediately: true`**：脚本在当前文档里立刻跑一遍，同时也注册给后续文档。
此刻目标停在首行之前、页面自己的脚本还没跑，所以补上去仍然赶在它读之前。
（读数：同一条探针变成 `uaFullVersion: 133.0.6943.127`。）

> **上面这句「赶在它读之前」是错的（2026-11-16 第三版纠正，CEO 三轮实测拍板）。**
> 那条读数是在 **CDP 会话里**读的，等于只证明「补丁装上了」；**子帧页面自己**读到的
> 仍是宿主真值 `157.0.8103.78`，8 秒内都不翻。详见文末「0.4.7.2 第三版」一节。
> 这一版按「已知缺陷」交付，判据口径也一并改成读页面侧。

### 修法二：版本号做实（读路径派生的 hints 不再一律打码）

`src/fingerprint/hints.js` 新增 `chromeVersionOf(ua)`：

- UA 里能解析出**三段以上**（`Chrome/133.0.6943.127`）→ 派生 / 对齐就用它本人；
- 只有 `Chrome/133`、`Chrome/133.0` 这种**没写全**的 → 仍回落 `<major>.0.0.0`。
  （UA 本来就没声称补丁号，打码不会自相矛盾；写全了还打码，才是一眼能看出的假。）

三条规则（有完整版本 / 无 hints / UA 解析不出）一条没改，只把「打码值」换成「UA 里那个值」。
**读路径仍然零写入**，写路径仍以 UA 为准。

## 0.4.7.2 第三版 · 子帧这条判据改成说真话（2026-11-16 CEO 三轮实测后拍板按 B 交付）

第二版报的「子帧 `uaFullVersion` 已补上」**不成立**，而且我的判据是**自己跟自己对上**的：
