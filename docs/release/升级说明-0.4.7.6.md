# FreePower 0.4.7.6 升级说明

> 本版**取代 0.4.7.5**。0.4.7.5 已经打成包、也推过 GitHub，但**真站验收没过**，不作为发布版；
> 0.4.7.6 在它的代码上补完最后三个根因。**包等验完再出**（出包口径见文末）。

这一版修的是「环境能开、代理预检也绿，但页面打不开」的三条真根因，外加你报的
「**窗口排列跨屏**」和「**窗口同步页整页布局**」。

## 1. 代理中继：槽位只覆盖一次拨号（`src/proxy/relay.js`）

### 1.1 参数（默认值，全部可用环境变量覆盖）

| 参数 | 默认 | 环境变量 | 含义 |
|---|---|---|---|
| 并发 | **8** | `FREEPOWER_RELAY_CONCURRENCY` | 同时**拨号**的连接数上限 |
| 排队上限 | **20s** | `FREEPOWER_RELAY_QUEUE_TIMEOUT_MS` | 拿不到槽位最多等多久；**与拨号预算无关** |
| 单次拨号 | **21s** | `FREEPOWER_RELAY_DIAL_TIMEOUT_MS` | 一次 TCP 连接上游的上限（让 TCP 重传跑完，见 §1.2） |
| 单连接拨号总预算 | **45s** | `FREEPOWER_RELAY_DIAL_BUDGET_MS` | 一条连接在「拨号」上最多花多久（含重试） |
| 拨号次数 | **2** | `FREEPOWER_RELAY_DIAL_ATTEMPTS` | 1–5 |
| 单连接总预算 | **60s** | `startRelay({timeoutMs})` | 「拨号 + 握手」预算，**从真正开始拨号起算** |

### 1.2 为什么单次拨号是 21s（8s 是我们自己定错的）

2026-11-18 21:40，CEO 在一台**今天没碰过的干净代理**（10057 `38.190.251.109:33066`）上直接量了
上游端口的建连行为：

```
8s 超时：并发 1 → 通 4/8（4 条 8s 超时）；并发 2 → 8/8；并发 4 → 8/8
21s 超时：并发 1 → 通 8/8  耗时 [124, 170, 204, 209, 1146, 3235, 4264, 15239]
          并发 8 → 通 8/8  耗时 [120, 121, 165, 171, 206, 213, 215, 1193]
```

看成功耗时：**120ms / 3.2s / 4.3s / 15.2s** —— 这是标准 TCP SYN 重传退避（1s / 3s / 7s / 15s）。
上游在丢 SYN，TCP 自己在重传，**我们 8 秒就掐断了，正好砍掉 15 秒那次重传**。

所以：

- 不是并发上限（并发 8 在 21s 下 8/8 全通）；
- 不是我们打坏的（10057 今天没碰过）；
- 是**拨号超时太短**，把 TCP 自己的恢复机制掐死了。

这一版只改这一个参数：单次拨号 **8s → 21s**，单连接总预算 **20s → 45s**（2 × 21 + 余量），
`dialAttempts` 仍 **2**、排队仍 **20s**、并发仍 **8**。**槽位只覆盖一次拨号、失败立刻还槽** 这条不动。

判据 `test/proxy-relay-syn-retransmit.test.mjs`（假上游 + `net.connect` 测试替身，不碰真代理）：
模拟 TCP 第 4 次重传（16s 才连上）——

- 产品默认 21s：`elapsed=16017ms`、`max_dial_ms=16012`、`dial_attempts=1`、`dial_retries=0`、隧道建成
  → **8 PASS / 0 FAIL**；
- 显式 8s 版本：客户端 `REP=4`、`tunnels=0`、`dial_attempts=2`、`dial_retries=1`、`max_dial_ms=8016`
  → 同一条判据红（证明 8s 会把能救回来的连接判死）。

### 1.3 为什么槽位只覆盖一次拨号

上一版（0.4.7.5 初版）是「一条连接拿着槽位一直重试」：

```
单次拨号 21s × 最多 3 次 ⇒ 一个槽位最坏被占 63s
8 个槽 × 63s ⇒ 吞吐 ≈ 每 8 秒 1 条
而 Chrome 一个页面要 30 条左右连接 ⇒ 页面 45s 必然超时
```

实测 `max_dial_ms=60015` 就是证据：一条连接在拨号上耗掉整整 60 秒，而同一时刻单发探这台代理
只要 649ms。**不是供应商不给连，是我们把自己的槽位饿死了。**

现在的做法：

- `dialUpstream()` 每次尝试前 `gate.acquire(queueTimeoutMs)`，`finally` 里**立刻 release**；
- 失败立刻还槽，再重新排队重试 —— 一条坏连接最多占 8 秒，不再占 20/60 秒；
- 握手**不占槽位**（慢握手不堵公共资源）；
- 排队超时与拨号超时**分开计数**，日志里能一眼分清「排队等死」和「拨号超时」。

### 1.4 `stats` 可观测字段

```
connections / tunnels / failed / active / peak_active / concurrency
queued / queue_depth / peak_queue / queue_timeout / queue_timeout_ms
max_queue_wait_ms / queue_wait_ms_total
dial_timeout / max_dial_ms / dial_ms_total
dial_attempt_ms / dial_budget_ms / dial_attempts_max / dial_attempts / dial_retries
dial_fail_kinds   ← {"timeout":N} / {"econnreset":N} …（区分上游慢与上游立刻拒绝）
client_closed     ← 浏览器自己 RST 掉的预连接（不是链路失败，单独记）
upstream
```

`failed` 只算**链路失败**（拨号/握手）。Chrome 启动和导航时会开几条 speculative socket 再丢掉
（真内核实测 13 条里 2–3 条），它们进 `client_closed`，判据口径因此是
`tunnels + client_closed === connections` 且 `failed === 0`。

凭据依旧不进任何日志面（只打 `127.0.0.1:<port> → 上游 host:port`）。
`close()` 先 `gate.drain()` 拒掉排队者，再 destroy socket，再关监听。

## 3. 代理预检：硬失败才拦启动，探测源挂了不算代理坏（`src/proxy/probe.js`）

### 3.1 失败分两类

| kind | 含义 | 处置 |
|---|---|---|
| `tcp` | TCP 连不上上游（超时 / 拒绝） | **硬失败**：拦启动（`800003 proxy_unreachable`） |
| `auth` | SOCKS/HTTP 握手被拒、认证失败、407 | **硬失败**：拦启动 |
| `target` | 上游连不上目标站（CONNECT 被拒等） | 软失败：按「未验证」启动 |
| `probe_site` | 探测站 429/403/5xx/空 body/格式不对、目标 TLS 失败 | 软失败：按「未验证」启动 |

- 探测源：主源 `ip-api.com`，备用源 `ipinfo.io`（`FALLBACK_PROBE_URLS`），与 `checkProxy` 同一套语义。
- **「所有探测源都不可达」不能判代理不可用**。`manager` 只记一条
  `proxy_probe_unavailable` 告警「探测源不可用（不是代理不通）…已按「未验证」启动」，**不抛 800003**。
- 起始页：软失败状态是 `warn`、标签「**探测源不可用**」、详情写「不是代理不通：…」；
  只有硬失败才写「代理未连通」。新增 `.status.warn` 样式。
- 浏览器内出口探测：只有落到 `chrome-error://` 才算 `kind:'proxy'`；空内容/格式不对算 `probe_site`。

### 3.2 判据（`test/proxy-probe-classify.test.mjs`，13 条）

- **红**：`3 PASS / 10 FAIL` —— `kind=undefined`、起始页把 429 写成「代理未连通」。
- **绿**：`13 PASS / 0 FAIL` —— 429 → `probe_site`、空 body → `probe_site`、TCP 不通 → `tcp`（硬）、
  认证失败 → `auth`（硬）、上游连不上目标 → `target`（软）、软失败起始页写「探测源不可用」且**不写**
  「代理未连通」、硬失败仍写「代理未连通」。

## 7. 窗口同步页整页布局（单独提交）

按逆向 `31-窗口同步页布局规格.md`（截图像素实测 + 远端 CSS 原文双源，宽度算式
`240+12+586+12+480+12=1342` 精确对上）重排，骨架从「竖排卡片」换成对手那套：

- 顶部操作条（高 40 + 下间距 12）：全部分组 ▾ / 启动同步（蓝实心，同步中换成红色「停止同步 (Ctrl+Alt+D)」）/
  重启同步 / 已选 N 列 ✕（有选中才出现）/ 右侧 ⚙
- 左：窗口列表表格卡（`flex:1; min-width:540; margin-right:12`），列宽照抄
  `复选框 40 / 序号 100 / 环境编号 100 / 分组 min80 / 环境名称 min90 / 状态 160 / 操作 100`；
  行高 56、表头 38 + 2px `#F8FAFF` 分隔线、偶数行 `#F8FAFF`、悬停 `#E8EDFF`、主控行整行 `#D2ECFF`
- 右：操作台卡（480 定宽）：标题条 60（操作台 + 桌面小组件开关）→ tabs 32（窗口管理 / 标签管理）→
  内容 padding 16。窗口管理里：显示窗口 + 统一大小（同一行各占 50%、高 40；统一大小未同步时
  disabled + tooltip）→ 窗口排列 → 显示器（内置屏幕 / 扩展屏幕 N + 分辨率）→
  「根据显示器的分辨率自动排列所选窗口」开关 → 一键排列 / 自定义排列
- **排列方式两个选项都摆**：`宫格平铺`（等分）/ `重叠平铺`（`x=工作区.x+30×i`、`y=工作区.y`、
  `宽=工作区宽−30×(n−1)`、`高=工作区高`，步长 30 硬编码）。两个模式下都渲染；唯一显隐：
  显示器选「全部屏幕」时重叠平铺不出现，只剩一个选项时**不摆 radio**。
- 「自定义排列」是自动排列开关**关掉**后的模式：按钮文案跟着变，按钮上方内联展开 4 行
  （起始位置 X/Y、窗口大小 宽/高、窗口间距 横向/纵向、窗口数量 个/行），改完不自动重排；
  4 个字段**记住上次的值**（`web/sync-prefs.js`，键 `fp.sync_arrange`，localStorage）。
- **同步运行中列表勾选被锁**：复选框 disabled + tooltip「同步进行中，停止同步后才能修改选择」；
  表格底部写明「同步启动后才打开的环境不会自动加入本次同步；需要停止同步后重新开始」。
- 状态列**只三态**：`同步中(主控)`（#1E4DFF / 500 + 图标）/ `同步中` + CSS 动画省略号 / `-`（#C9CAD1）；
  未同步时显示 `主控窗口` / `被控窗口`。表格里**没有**「同步异常」（那是操作台的）。
- 空态三行居中在**表格区**：暂无已打开的浏览器环境 / 打开2个浏览器，即开启窗口同步操作 / 前往打开。
- **一处故意偏离对手**：操作列做成右侧固定列。对手在 1342 窗口下这列被挤进横向滚动区、
  得滚才看得见，我们不抄这个毛病。

**没有摆的（宁可少一项，也不摆点了没用的开关）**：AI 自动操作、外观（主控窗口颜色）、
仿真操作（输入/点击速度）、文本组/文本管理、帮助中心。判据里有一条专门扫这个。

顺带保留会话读数条（表格底部）：已转发 / 被开关拦下 / 文本已发 / 已发出 —— 改版不能把
「同步到底有没有在干活」的唯一依据弄丢。它是读数，不是控件。

### 9.3.4 链式上游：本机 → 本地 SOCKS5 链 → 环境代理（0.4.7.7 候选，包后代码）

§9.3.3 的结论是「卡在到代理这一跳的 SYN 丢包」。逆向随后给了一条关键事实：**AdsPower 的页面流量
在本机一条都没拨到那台代理** —— 全机器 TCP 采样 545 个样本 × 100ms（覆盖 IPv4+IPv6），对
`206.119.169.175:37663` 的 ESTABLISHED / SYN_SENT 全是 0，本机也没有任何本地中继；页面走的是
`127.0.0.1:10808`（用户的 v2rayN），**但出口仍是 `206.119.169.175`**。也就是说它把「拨这台代理」
放到了隧道对端（泰国节点）去做，绕开了本机到那台代理的丢包路径。

CEO 在 `206.119.169.185` 上做了串行对照（不并发）：**经 10808 链式 6/6 全通**（到目标 1391 / 2994 /
2228 / 1173 / 1959 / 1297ms）；**直连 5/6**（一次 22049ms 读超时、一次 TCP 建连 3202ms）。
串行下直连还能凑合，一上并发就崩（31/48 都烧在 TCP 段）。

**本版实现**（`src/proxy/relay.js` + `src/proxy/system-proxy.js` + `src/runtime/manager.js`）：

```
浏览器 → 我们的中继(127.0.0.1:port)
       → 本地 SOCKS5 链(默认读系统代理，如 127.0.0.1:10808)
       → 在隧道里 CONNECT 到环境代理 host:port
       → 在隧道里对环境代理做 SOCKS5（带它的账号密码）→ CONNECT 目标
```

- **出口仍是环境代理的 IP**：最后一跳 CONNECT 目标的是内层（环境代理），不是本地链的节点。
- **默认开**：系统代理（`HKCU\...\Internet Settings`，`ProxyEnable=1`）里是**显式 SOCKS**
  （`socks=` / `socks5=`）时自动走链；HTTP 系统代理不能当 SOCKS 链用，会退回直连。
- **开关**：`FREEPOWER_RELAY_CHAIN=0|off|false` 关掉；`FREEPOWER_RELAY_CHAIN=socks5://host:port`
  显式指定（优先于系统代理）。
- **兜底**：链连不上 / 外层握手失败 → **退回直连**，记 `chain_fail`，不拦启动、不拦连接。
  **内层（环境代理）认证失败/拒绝不退回直连** —— 那等于绕过用户配的代理，必须照实报错。
- **范围**：只有「中继拨上游」这一条路走链；本地 API、下载、CDN 一律不走链。

`stats` 新增（只记读数、不含凭据）：`chain`（`host:port` 或 `null`）、`chain_used`、`chain_fail`、
`chain_tcp_ms` / `chain_tcp_ms_total`（连本地链）、`chain_reply_ms`（让链 CONNECT 到环境代理）。

**判据 `test/relay-chain.test.mjs` 5/0**（假上游：两层 SOCKS5 + 本地 HTTP 服务，不碰真代理）：

| # | 断言 |
|---|---|
| ① | 两层套起来能通：页面 `relay-ok` 真穿过链；外层**只看到 CONNECT 到内层 host:port**、没收到环境代理凭据；内层才是连目标那一跳，凭据 = 环境里配的；`chain_used=1`、`tunnels=1`、`failed=0` |
| ② | 链不可达（关掉的端口）→ 退回直连、页面仍出内容；`chain_fail≥1`、`chain_used=0`、`tunnels=1`、`failed=0` |
| ③ | 内层认证失败 → **不**退回直连；`chain_fail=0`、`chain_used=0`、`dial_fail_stage.auth≥1` |
| ④ | 开关解析：`0/off/false` 关、`socks5://` 与裸 `host:port` 指定、`http://` 不认 |
| ⑤ | `chain=null` 行为与直连完全一致（回归） |

**真代理还没验**（等统一窗口，一台、一次、两站各 45s）。判绿标准不变：站1 title 含 `xPoints`、
正文有 `Connect Wallet`；站2 不是 chrome-error。验的时候要看 `stats.chain_used` 是否 > 0 ——
若 `chain_fail` 一直涨，说明本地链本身没起（10808 没开/不是 SOCKS），那时页面走的是直连。

### 9.4 与 0.4.7.4 的对照

0.4.7.4（无界并发 + 10s 超时）在**健康**代理上曾完整渲染 `defi.xstocks.fi/points`；
0.4.7.5 初版（并发 4 + 排队复用 60s 预算）在同一台代理上两站全 chrome-error，`queued=25`、
`lastError=queue_timeout` —— 那是「限制并发做成排队等死」，§1 已修。

但修完之后仍然打不开。21:21 在干净代理 10057 上的读数（§9.3.1）说明既不是排队、也不是并发上限，
而是**拨号超时 8s 砍掉了 TCP 第 4 次重传（15s）** —— 21:40 的端口级实测把机制钉死了（§1.2）。
**产品侧能做的已经做完**：有界队列、拨号预算与排队分离、槽位只覆盖一次拨号、拨号重试、
探测源软失败放行、砍后台连接；这一版再把单次拨号放到 **21s / 总预算 45s**，让 TCP 自己恢复。
剩下的仍取决于上游是否持续丢 SYN —— 没有任何配置能保证一条**始终连不上**的链路开出页面。

这一版还补了一条**全链路判据**（`test/relay-e2e-kernel.test.mjs`，真内核）：
浏览器 → 我们的中继 → 本地假 SOCKS5 → 本地 HTTP 页面。绿的时候 `title`/正文/6 张跨域名图
全部真渲染，`connections=14 tunnels=14 failed=0 queue_timeout=0 max_dial_ms=1`；
把中继退回旧逻辑（槽位覆盖握手）并压到 2 个槽位时立刻红（`queue_timeout=9`、`tunnels=10/19`、
6 张图只出 2 张）。**这条证明链路本身能渲染页面 —— 今天打不开的原因在上游拨号，不在链路。**

### 9.5 上一版构建的两次读数（历史，保留）

### 9.6 本版怎么验（不再刷真代理）

1. 用户按平时用法**开一个环境**：看第一张标签是不是起始页、出口 IP 有没有值；
2. **43 个环境逐个单开**（一次一个、不并发），记录每个能开/不能开；
3. 判读口径：**先看单发串行是否也慢/超时** —— 单发就能复现 15s 重传或 21s 建连超时 ⇒ 到代理这一跳丢 SYN
   （2026-11-19 实测已排除并发上限与速率限制）；**单发一直很快、只在产品里大面积失败** ⇒ 才回来找产品。

工具：`tools/fingerprint-sweep.mjs`（不进 asar），逐个环境串行、两站各等 45s、
每个环境跑完确认进程退出，输出 JSON + Markdown 表。参数：

```
--limit N        只跑前 N 个
--skip a,b       跳过这些环境 id（可多次）
--only a,b       只跑这些
--db <path>      环境库（默认 .tmp/db-1118/freepower.db 只读副本）
--wait ms        每站等待（默认 45000）
--out <dir>      输出目录
--keep           保留环境不关（调试用）
```

失败归类**判别器是「单发 checkProxy 通不通」**（不并发、不经中继、只探一次）：
`代理` = 单发就 TCP 不通/握手被拒；单发通而产品里不通 → **不许归代理**，按中继读数归 `中继`
（`queue_timeout`/`dial_timeout` 且隧道数 < 连接数一半）或 `产品`；页面通了但被拦/标题不符归 `指纹`；
单发只是探测源不可用（软失败）→ `我核不了`，不猜。

**全量 43 本版没跑**（上游当天已被打退化，跑等于继续打），所以本版**没有全量通过读数**。

## 10. 已知限制（这一版**没修**，如实写）

**本版未做（引擎没有对应能力，界面上也不摆）**：外观（主控窗口颜色）、仿真操作（输入/点击速度、
延迟点击/输入）、文本组（文本管理 tab）、AI 自动操作。宁可少一项，也不摆一个点了没用的开关 ——
判据里有一条专门扫这个（`test/sync-layout.test.mjs` ④）。

**480×680 小组件窗本版不改**：牵动 README、`docs/20` 与兜底常量，收益不值这个风险。
操作台小窗实际尺寸 **430×620**，本版没有动它。

1. **内核启动仍会发 3 个后台请求**（`--disable-background-networking` 等 8 个 flag 关不掉，
   属 headed Chrome UI 自身行为）。用 netlog 抓到的 URL：
   - `accounts.google.com/ListAccounts?...`（Chrome 登录态）
   - `www.gstatic.com/ohttp_gateway/hpke_public_keys/v1/sbc_prod?...`（隐私沙箱 OHTTP 公钥）
   - `www.google.com/async/folae?...`（地址栏 zero-suggest）
   已试过无效：`--disable-account-consistency`、`--dns-prefetch-disable`、`--disable-breakpad`、
   `--disable-features=PrivacySandboxOhttp,IpPrivacyProxy,IpPrivacyProtection,PrivacySandboxSettings4,OmniboxZeroSuggest,OmniboxOnFocusSuggest,AccountConsistency,SigninPromo,ChromeSignin`。
   **结论：这 3 个关不掉**，但它们不抢中继槽位（有界队列已兜住）。
2. **跨站子帧里页面自己读到的 `uaFullVersion` 仍是真实内核版本**（0.4.7.2 起的已知缺陷，沿用）：
   `brands` / `fullVersionList` / `platformVersion` 从首字节起就对；同站子帧跟随父页，本来就对。
   计划 0.4.8 处理（给 OOPIF 补完补丁后 reload 一次，需评估副作用）。
3. **`profile.kernel_version` 取目录名**：Chrome 更新落盘但未生效时，比实际内核新一个补丁号。
   计划 0.4.8 修（涉及「还没启动就要知道内核版本」的先有鸡还是先有蛋问题）。
4. **上游代理冷启动第一发可能 35s+**：中继已放宽到 60s，但探测链路的 3 次退避合计仍约 5.5s，
   极端情况下起始页可能先显示「未连通」，点「重新检测」即通。
5. **上游丢 SYN 时，TCP 重传要 15s 才放弃**：这是本版查实的真实机制（不是「并发黑洞」）。
   上游在丢 SYN，TCP 自己按 **1s / 3s / 7s / 15s** 重传；实测成功耗时 120ms / 3.2s / 4.3s / **15.2s**。
   上一版把单次拨号定成 8s，**正好砍掉 15s 那次重传**，把能救回来的连接判死。
   本版改成单次 **21s**、总预算 **45s**，让 TCP 自己恢复；但链路若**始终**连不上，
   页面仍会打不开 —— 遇到时先重试一次，仍不行就换代理。
6. **探测源不可用时会按「未验证」启动**：此时起始页写「探测源不可用（不是代理不通）」，
   不代表代理坏了；等探测源恢复后点「重新检测」。
7. **本版没有全量 43 通过读数**：验证方式改为「用户真机单开 + 43 环境逐个单开」（见 §9.6）。
8. **上游对单源 30+ 连接扇出丢 SYN 时，页面仍会打不开**（本版读数见 §9.3.2，四台三网段同形态）：
   单发 0.86–3.24s 能连，但页面扇出 30+ 条时，35–48 次拨号全部烧满 21s 仍连不上，页面 45s 先放弃。
   产品侧策略已验证不是瓶颈（`queue_timeout≈0`、`peak_active=8`、槽位只覆盖一次拨号、失败立刻还槽）。
   **遇到时：重试一次；仍不行就换代理或等上游恢复**，不要指望调大并发/调长超时能救 —— 那只会把扇出压得更死。
   **到代理这一跳存在 SYN 丢包，单发串行即可复现**（15124ms 重传 / 21037ms 建连超时）；
   页面需 40+ 条连接时部分连接会撞上丢包而超时，**代理单发再快页面仍可能打不开**。
   实测已排除并发上限与速率限制（16 并发、16 条/秒均 16/16 全通）。
9. **链式上游依赖本机确实有一条可用的 SOCKS5 链**：默认读系统代理，`ProxyEnable` 没开或系统代理是
   HTTP 代理时会退回直连（`stats.chain_fail` 会涨）。此时页面走的还是「本机 → 环境代理」那条丢包路径，
   第 8 条的限制照旧。关掉开关：`FREEPOWER_RELAY_CHAIN=0`。
