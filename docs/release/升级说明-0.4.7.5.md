# FreePower 0.4.7.5 升级说明

> **未发布。** 本版已打包、也推过 GitHub，但真站验收未通过，不作为发布版；
> 发布说明以 `升级说明-0.4.7.6.md` 为准。

这一版修的是「**打开环境没有真页面 / 起始页说代理未连通**」的根因，外加你报的「**窗口排列跨屏**」。

用户看到的现象是：环境能开、代理预检也绿，但页面打不开，起始页写着「代理未连通」。
查下来是**四个原因叠在一起**，这一版逐个拆掉：

| # | 根因 | 这一版怎么改 |
|---|---|---|
| 1 | 内核启动瞬间对中继开 **14 条连接**，其中 10 条是 Google 后台；中继每条都现拨上游，上游排队 10.6s 才连上，超过中继 10s 超时 → `ERR_SOCKS_CONNECTION_FAILED(-120)` 81 次 | 中继改**有界并发队列**（默认 **8**）+ 超时 10s → **60s**；排队（45s）与拨号（60s）预算**分开计** |
| 2 | 那 10 条后台连接本来就不该发 | 启动参数加 **8 个 flag** + 关掉网络时间服务 |
| 3 | 出口探测**一次失败**就写「代理未连通」，而冷启动第一发实测要 35.5s | 探测改**3 次退避**（0 / 1.5s / 4s），并**走中继**（与浏览器同一条链路） |
| 4 | 排列把显示器 id 夹到 `[-1,999]`，真 id 是大整数 → 回落到左屏；`displays.json` 里两块屏 `primary` 都是 false | id 原样保留按字符串比对；桌面壳按 `getPrimaryDisplay().id` 写主屏 |

## 1. 代理中继：有界并发 + 60 秒超时（`src/proxy/relay.js`）

- 上游拨号改成**有界并发队列**，默认 **8**，可配：
  `startRelay(upstream, { concurrency })` 或环境变量 `FREEPOWER_RELAY_CONCURRENCY`。
- 队列只覆盖「**拨号 + 握手**」这一段，隧道一建好立刻放槽位 —— 长连接不占槽位。
- 单连接超时 **10s → 60s**（依据：冷启动第一发实测 35,572ms 才通，30s 都偏紧）。
- `stats` 新增可观测字段：`queued` / `queue_depth` / `peak_queue` / `active` / `peak_active` /
  `concurrency` / `timeout_ms` / `upstream`。
- 超时与失败进 `stats` 和 `lastError`，**凭据依旧不进任何日志面**（只打
  `127.0.0.1:<port> → 上游 host:port`）。
- `close()` 先 `gate.drain()` 把排队者全部拒掉、再 destroy 所有 socket、再关监听 —— 不漏端口。

### 1.1 上游拨号重试（同一版追加，实测逼出来的）

有界队列只解决「自己把上游打满」，解决不了**上游丢 SYN**。本轮实测（真上游 10055，2026-11-18）：

```
串行 5 次 checkProxy：5/5 通（16452 / 626 / 7518 / 1104 / 668 ms）
4 并发 14 条打中继：只成 3 条，lastError = 连不上上游 …：connect ETIMEDOUT（每条等约 21s）
```

一次丢包就报废一条浏览器连接，页面自然打不开。所以补上：

- 单条连接拨上游**最多试 3 次**（`dialAttempts`，可配 1–5，环境变量 `FREEPOWER_RELAY_DIAL_ATTEMPTS`）。
- 每次拨号上限 **21s**（Windows 上 SYN 被丢的 `ETIMEDOUT` 就是这个数，再等没有意义），
  总预算仍受 60s 约束，不会把预算花光。
- **只有「连不上」才重试**；握手阶段失败（密码错、上游拒绝）不重试 —— 那是配置问题，
  重试只会把错误拖成超时。
- `stats` 新增 `dial_attempts` / `dial_retries`。

### 1.2 并发 4 → 8，排队预算与拨号预算分开（2026-11-18 18:40，最后一次调参）

§7 那趟真站验收（29 条连接只成 3 条隧道、`queued=25`、`lastError=queue_timeout`）不是
「上游彻底坏了」，而是**我们自己的有界队列把连接饿死了**：

```
并发 4 × 单次拨号 21s × 3 次重试 ⇒ 一个槽位最坏被占 63s
吞吐 ≈ 每 16 秒 1 条连接 ⇒ 29 条要 7 分钟
而排队中的连接，60s 预算**从连上中继那一刻就开始计**，还没轮到拨号就先超时
```

`queue_timeout` 这个 lastError 就是证据：它压根没去拨上游。旧版无界并发（实测 14 条一起拨）
反而能渲染页面，说明问题不在「并发本身」，在「排队等死」。这一版改三处：

1. **默认并发 4 → 8**（`FREEPOWER_RELAY_CONCURRENCY` 仍可配）。
2. **排队预算独立**：`queueTimeoutMs` 默认 **45000**，不再复用 `timeoutMs`；
   60s 是「拨号 + 握手」的预算，**从真正开始拨号那一刻起算**。排队超时与拨号超时分开计数：
   `stats.queue_timeout` / `stats.dial_timeout`，不再混成一个 `lastError`。
3. **`stats` 加排队/拨号耗时读数**：`max_queue_wait_ms`、`queue_wait_ms_total`、
   `max_dial_ms`、`dial_ms_total`、`queue_timeout_ms`。下次再出问题，一眼看出是排队还是拨号。

**没有动**：单次拨号 21s、重试 3 次、60s 拨号预算（21s 是 Windows 上 SYN 被丢的实测值，
串行 checkProxy 有 16.4s 的先例，改小会误杀慢代理）。

判据 `test/proxy-relay-queue-budget.test.mjs`（假上游 + TEST-NET 黑洞，不碰真代理）：

```
改前（并发 4 / 排队复用 60s）：2 PASS / 15 FAIL
  读数：concurrency=4、queue_timeout_ms=undefined、dial_timeout=undefined
        ③ 排队 3s 后第 3 条连接被 2500ms 的「排队预算」砍掉 → 通 2/3
改后：17 PASS / 0 FAIL
  读数：concurrency=8、queue_timeout_ms=45000、timeout_ms=60000
        ② queue_timeout=4、dial_timeout=0、max_queue_wait_ms=700、
           上游 connections=2（排队的 4 条一次都没拨到上游）
        ③ 排队 3014ms 后拨号仍拿到完整 2500ms 预算 → 3/3 通
        ④ 黑洞上游 dial_timeout=1、max_dial_ms=600、queue_timeout=0
```

## 8. 已知限制（这一版**没修**，如实写）

**本版未做（引擎没有对应能力，界面上也不摆）**：外观（主控窗口颜色）、仿真操作（输入/点击速度、
延迟点击/输入）、文本组（文本管理 tab）、AI 自动操作。宁可少一项，也不摆一个点了没用的开关 ——
判据里有一条专门扫这个（`test/sync-layout.test.mjs` ④）。


1. **内核启动仍会发 3 个后台请求**（`--disable-background-networking` 等 8 个 flag 关不掉，
   属 headed Chrome UI 自身行为）。用 netlog 抓到的 URL：
   - `accounts.google.com/ListAccounts?...`（Chrome 登录态）
   - `www.gstatic.com/ohttp_gateway/hpke_public_keys/v1/sbc_prod?...`（隐私沙箱 OHTTP 公钥）
   - `www.google.com/async/folae?...`（地址栏 zero-suggest）
   已试过无效：`--disable-account-consistency`、`--dns-prefetch-disable`、`--disable-breakpad`、
   `--disable-features=PrivacySandboxOhttp,IpPrivacyProxy,IpPrivacyProtection,PrivacySandboxSettings4,OmniboxZeroSuggest,OmniboxOnFocusSuggest,AccountConsistency,SigninPromo,ChromeSignin`。
   **结论：这 3 个关不掉**，但它们不抢中继槽位（有界队列已兜住）。
2. **跨站子帧里页面自己读到的 `uaFullVersion` 仍是真实内核版本**（0.4.7.2 起的已知缺陷，沿用）：
   `brands` / `fullVersionList` / `platformVersion` 从首字节起就对；同站子帧跟随父页，本来就对。
   计划 0.4.8 处理（给 OOPIF 补完补丁后 reload 一次，需评估副作用）。
3. **`profile.kernel_version` 取目录名**：Chrome 更新落盘但未生效时，比实际内核新一个补丁号。
   计划 0.4.8 修（涉及「还没启动就要知道内核版本」的先有鸡还是先有蛋问题）。
4. **上游代理冷启动第一发可能 35s+**：中继已放宽到 60s，但探测链路的 3 次退避合计仍约 5.5s，
   极端情况下起始页可能先显示「未连通」、点「重新检测」即通。
5. **上游对突发连接丢 SYN 时，单个页面仍可能打不开**：这一版做了有界并发（8）、60s 拨号预算、
   拨号重试（3 次）与砍后台连接，但**没有任何配置能保证一个已经丢包的上游开出页面**。
   遇到时先重试一次；仍不行就换代理。这一条是上游行为，不是产品开关能解决的。
