# 带凭据代理走本地中继（0.4.7.3 任务 A）

> 一句话：**Chrome 内核不支持 SOCKS5 认证**，所以我们自己在本机起一个 SOCKS5 服务端，
> 对浏览器不要求认证、对上游用环境的账号密码握手。内核只看到 `127.0.0.1:<port>`。

## 1. 事实（用户报的「50 个环境全打不开」到底是什么）

用户机器上 0.4.7.2、50 个环境**全部**是 `socks5` + 用户名密码（`user_proxy_config` 里
host/port/username/password 都有、`proxy_id` 为 null，导入没问题）。启动日志：

```
代理预检通过 38.190.239.119 HK 8489ms
launch … --proxy-bypass-list=<-loopback> --proxy-server=socks5://38.190.239.119:33066
WARN 出口探测失败 出口探测页不是预期格式：This site can't be reached
```

直连那台 SOCKS5 做握手探测：客户端只报 `no-auth(0x00)` 时服务端回 **`0x02`（必须用户名密码）**。

**根因**：`--proxy-server=socks5://host:port` 只会发 no-auth，服务端要求 0x02 → 握手失败 →
所有请求 `ERR_BLOCKED_BY_CLIENT` / 页面全红。而我们的 `checkProxy` 在 Node 侧**带凭据**，
能过 → **预检绿、浏览器死**。这不是导入坏、也不是代理坏，是内核能力边界。

## 2. 修法：本机 SOCKS5 中继（`src/proxy/relay.js`）

```
浏览器 --socks5://127.0.0.1:<port>--> relay.js（对浏览器不要求认证）
       --(上游协议 + 环境凭据)--> 上游代理 --> 目标
```

- 只 bind `127.0.0.1`、端口 `listen(0)`（**绝不 0.0.0.0**，否则局域网里谁都能白用这个出口）；
- 上游是 `socks5`：greeting 同时给 `no-auth + userpass`，服务端挑 `0x02` 就走 RFC1929；
  CONNECT 用**域名形式**（`ATYP_DOMAIN`）—— 由上游去解析，出口国家不会被本机 DNS 破坏；
- 上游是 `http/https`：`CONNECT host:port` + `Proxy-Authorization: Basic base64(user:pass)`；
- 隧道建立后**裸 pipe**（不解析、不改字节）；
- 对浏览器只给 `M_NOAUTH`，只支持 `CMD_CONNECT`（其余回 SOCKS5 码并记账）；
- `close()` **先 destroy 所有 socket 再 close 监听**（否则反复起停会漏端口）；
- `lastError` / `stats` 记上游失败原因与计数，**不含凭据**。

### 接线（`src/runtime/manager.js`）

位置：代理预检**之后**、`buildArgs` 之前（`2.2` 块）。

| 条件 | 行为 |
|---|---|
| `proxyBound && chain.mode !== 'chain' && (username \|\| password)` | 起中继；`effectiveProxy = {type:'socks5', host:'127.0.0.1', port:relay.port, username:'', password:''}`；`chain_mode='relay'`；`proxyAuth=false` |
| 起不来 | `800003` + `reason='proxy_relay_failed'`，**拒绝启动**（绝不降级直连） |
| 不带凭据的 socks5 | **保持直连**（Chrome 自己能跑，多一层中继没必要） |
| 多级代理链 | 仍走 `chain.js` 那条路（`chain.mode === 'chain'` 时不进中继） |

生命周期：`stopProfile` / 内核自己 exit / 启动失败 catch / 拼参数 catch，**四条路径都 close**。

**预检仍然打真实上游（带凭据）**，不改成探本地中继 —— 否则「预检绿」就变成「探自己」，
正是这一版要修的假绿灯，不能换个地方再造一个。

`installRequestGating` 的 `proxyAuth` 在 `chain` / `relay` 两种模式下都是 `false`
（不再往页面发认证挑战；认证在 FreePower 这一侧完成）。

### 凭据可见面

- 命令行：`--proxy-server=socks5://127.0.0.1:<port>`，**没有上游 host/port、没有账密**；
- 启动响应 / 环境日志 / 页面 `navigator` 可见面：查不到账号密码；
- 日志只打 `代理中继 127.0.0.1:<port> → 上游 socks5 host:port`。

## 4. 已知限制（别读成「凭据代理全无破绽」）

1. **中继对浏览器不要求认证，只靠「只 bind 127.0.0.1」护着**：本机上任何进程都能连
   `127.0.0.1:<port>` 白用这个出口（端口是随机的，但同机可扫）。这与「本机多用户互不设防」
   是同一条信任边界（README 已知限制 17）。
2. **http/https 带凭据的代理现在也走中继**，不再走 CDP `Fetch.authRequired`。
   少一层页面可见的挑战，代价是多一次本地回环转发（实测对页面无影响）。
3. **`https` 代理 + `https` 目标（TLS in TLS）预检仍不支持**（既有边界，没变）。
4. 中继只支持 `CONNECT`（TCP）。UDP ASSOCIATE 不做 —— Chrome 的代理 UDP 走 `disable_non_proxied_udp`
   那条路，本来也不经过这里。
