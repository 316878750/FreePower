## 0. 一句话结论

用户抱怨的「配了没反应」有两层成因，这一版把两层都处理掉，并且**加了一条判据防止它再长回来**：

1. **写法层**：字段能填、能存、能 API 读写，但行为层没有一行代码读它 —— 这是「忘了接」。
2. **内核层**：字段被读了，但它落的是对手**定制内核的私有键**（`StaticConfig` / `DynamicConfig`
   里的 `DeviceName` / `MacAddress` / `NetFilters` / `TTSEngines` / `BlockPage` / `FoaceSafeBrowsing`…）。
   我们用官方 Chrome for Testing，**一个都不读** —— 这一类写多少代码都不会生效。

两类都只有一个出口：**接上（必须能指出消费路径且有证据）**，或**禁用并把原因写在界面上**。

### 2.1 `disable_video` 为什么没被禁用（与 CEO 裁决的差异，**CEO 已复核批准**）

CEO 的原裁决是「对手走 `StaticConfig.NetFilters`，需内核 → 禁用」。复核代码后我认为这条前提
在我们这儿不成立，所以**没有禁用**。CEO 2026-11-15 复验后确认：「我那条裁决的前提是错的，
维持接线，不用改。」

1. 我们的实现不是靠内核私有键，而是 **CDP `Fetch` 请求拦截**（`src/kernel/net-rules.js` 的
   `isMediaRequest` / `decideRequest`），按与对手同样的三条 mime 判：`video/*`、
   `application/vnd.yt-ump`、`application/vnd.apple.mpegurl`，外加 `resourceType=Media`；
   request 阶段判一次、**response 阶段再判一次**（HLS/yt-ump 伪装成 XHR 的情况）。
2. 它有**真内核证据**：`test/switches.test.mjs` 的 `disable_video=1` 用例断言「服务器侧媒体命中 = 0」、
   「`<video>` 停在 readyState=0 / networkState=3」、「图片不受影响」。纯函数判定在
   `test/net-rules.test.mjs`（12 条）。
3. 按 CEO 自己那条硬规则「接上 = 能指出消费路径 + 有证据 + 真内核实测生效」，它满足；
   禁用反而是**能力倒退**（那正是用户最反对的方向）。

#### 三个字段的待遇为什么不同（这条别再搞混）

| 字段 | 走哪条路 | 官方内核能不能做 | 本版待遇 |
|---|---|---|---|
| `disable_image` | `--blink-settings=imagesEnabled=false`（标准 Chromium 参数） | 能 | **接线** |
| `disable_video` | CDP `Fetch` 拦截（三条 mime + `resourceType=Media`） | 能 | **接线** |
| `image_size` | `StaticConfig.NetFilters[{mimeType, maxSize}]`（**定制内核私有键**） | **不能** | **禁用** |

**`image_size` 禁用 ≠ `disable_video` 也该禁用。** 前者的能力缺口在「按字节数卡阈值」这个语义上，
后者只是「按 mime 类型拦」，两者在 CDP 层根本不是一个难度。这条区分同时写进了
`test/unit.test.mjs` 判据 ⑨ 旁边的注释，免得后人看 `image_size` 被禁就顺手把 `disable_video` 也禁了。

**边界照实说**：`switches.test.mjs` 的真内核读数在 0.4.6 这轮**没有重跑**（单租户窗口，见 §7）；
引的是既有读数。但本版新增的两条 B 层判据（§2.3）已经在真内核上跑过，证明内核调用链本身是好的。

### 2.2 顺带接上的：`cookie`（登录 cookie 写进内核）

`cookie` 属于「能存能取、启动链路一次都没读」那一类（`21-` §5 名单里），txt 导入整批带着它，
但启动后仍是游客态。本版在 `src/runtime/manager.js` 加了 `loginCookiePlan()`（纯函数）+ 启动时
`Storage.setCookies`：

- 结构化 cookie（AdsPower 形状）原样写；原始串 `sid=xxx; uid=7` 按 `;` 拆成对，**挂到
  `open_urls[0]` 的 host**（退一步 `domain_name`），两个都没有就**如实失败**，不猜域名；
- **早于第一张页面导航**写入（否则首帧就是未登录态，站点会把「未登录」写进 sessionStorage）；
- 失败不拦启动，逐条原因进日志。
- 复用既有 `src/kernel/cookies.js` 的 `writeCookies`（cookie 导入接口一直在用同一个函数）。

**没验的部分**：见 §2.3 —— 已补真内核判据（`test/login-cookie-kernel.test.mjs`），不再是「只有纯函数单测」。

### 2.3 这两条接线的**真内核判据**（0.4.6 第二轮补的）

第一轮交付时我说「真 Chrome 套件没跑，所以 `cookie` 启动写入与 `clear_cache_after_closing` 的真窗口
读数都没有」——CEO 指出这不行：这两个恰恰是本版唯一真正改变运行时行为的改动，比修 71 个禁用重要得多，
而全仓库（含 smoke 19 段）**没有任何一条判据覆盖它们**。补了两条 B 层判据，都在 `npm run smoke` 里：

**A. `test/close-purge-kernel.test.mjs`（16 条，`npm run test:close-purge-kernel`）**

| 判据 | 为什么必须有 |
|---|---|
| 对照：`'0'` → 停止后 1 秒还在、6 秒仍在、日志无痕 | **只有「删了」不能证明是这个字段干的**（别的路径顺手删了也照样「没了」） |
| 正例：`'1'` → 启动后目录有内核落盘的东西（不是空壳） | 先证明「有东西可删」 |
| 正例：停止后 **1 秒时目录还在** | 钉住「2 秒延迟」这条照抄来的语义（立刻删在 Windows 上必撞占用） |
| 正例：停止后约 2 秒目录**真的没了**（实测 1650ms 消失） | 主体结论 |
| 正例：日志里有「已删除内核数据目录」 | 删了要留证据，不是静默走运 |
| 正例：只删 `userdata` 这一层，**父目录还在** | 防「删过头」（删到 `profiles/<no>_<id8>` 或更上层就是另一个事故） |
| 对照环境的数据目录仍在 | 判据自己没删错对象 |
| 清完再启动：能起、目录重建 | 不是「删一次就再也起不来」 |

数据根用 `os.tmpdir()` 下的一次性目录，**绝不碰仓库里的 `data/`**（这条判据会真删目录）。

**B. `test/login-cookie-kernel.test.mjs`（19 条，`npm run test:login-cookie-kernel`）**

判的是**页面自己看得见的东西**，不是「CDP 里存着一条」：

| 判据 | 说明 |
|---|---|
| 0. 纯函数 5 条 | 结构化对象 / 无域名如实失败 / 原始串按启动网址挂上 / 乱码串记失败 / 空值静默 |
| A. 配了 cookie → 启动后 `document.cookie` 里真有它 | 用户视角：一启动就是登录态 |
| A. 日志有「已写入」且**日志里没有 cookie 的值** | 登录凭据不许被顺手打进日志（反查断言） |
| B. 对照组：不配 → 页面和内核里都没有 | 证明 A 的「有」是这个字段给的 |
| C. 乱码 cookie → 环境**照样起得来**、页面照常 load 完、日志有 WARN | 「导入的脏数据把环境锁死」比「cookie 没写进去」更糟 |
| D. 原始串 `a=b; c=d` + 启动网址 → 两个键都写进去 | txt 导入那条路走通 |

C 段有一处**故意的设计**：坏 cookie 那条**必须给启动网址**。不给的话「没域名可挂」本身就会记一条失败，
日志里照样有 WARN —— 判据就分不清是哪个原因红的。给了网址之后，唯一的失败来源才是「这串东西里
一个 `name=value` 都没有」。这一点是先红后绿时发现的：第一版没给网址，把 `pairs` 守卫关掉判据仍然是绿的。

**先红后绿（都实跑）**：
- 红：`manager.js` 的 `cache_purge_on_close` 改成 `false` → close-purge 判据红 2 条（「6 秒后仍存在」+「日志里没有删除痕迹」），其余 14 条仍绿 → 说明它只盯这一个字段，不连坐。
- 红：注掉 `await seedLoginCookies(...)` → cookie 判据红 6 条（内核 0 条 / 页面 document.cookie 长度 0 / 无「已写入」日志 / 坏 cookie 无 WARN / 原始串两条全红），其余 8 条绿。
- 红：只关掉「切不出 name=value 就记失败」那一条守卫 → **只红 1 条**（坏 cookie 的 WARN），环境仍照常起 → 证明这条断言钉的正是这个守卫，不是别的路径。
- 绿：恢复后 16 PASS / 0 FAIL、19 PASS / 0 FAIL，内核 `157.0.8103.78`。

## 3. 禁用的（71 个：57 个「本版做不到 / 不适用」+ 14 个云端专属）

### 3.1 本版做不到 / 不适用（57）

| 类别 | 字段 | 原因（页面上那一行） | 证据 |
|---|---|---|---|
| 内核私有键 | `device_name`、`device_name_switch`、`mac_address_config` | 网页读不到真 MAC / 设备名不出现任何接口，只保存不注入 | `30-` §6（`StaticConfig.DeviceName/ProductType/MacAddress`，且「哪个 API 变无证据」） |
| 内核私有键 | `image_size` | 不支持按大小限制图片，只能整页关图 | `30-` §5（`NetFilters{mimeType,maxSize}`） |
| 内核私有键 | `whitelist_open` | 白名单放行表用「域名白名单」，这一项不参与判定 | `30-` §4（`DynamicConfig.WhiteList` + `BlockPage`；**`whitelist` 非空才是白名单开关**，`whitelist_open` 只是额外放行清单） |
| 内核私有键 | `speech_voices` | 只用「语音合成」开关，音色列表不参与 | `30-` §8（`TTSEngines`，仅移动内核） |
| 死链 | `disable_console` | 无法禁用浏览器控制台（要改内核层） | `30-` §3（对手 11 处全是赋值透传，`IS_DISABLE_CONSOLE` 无读取者） |
| 没有落点 | `disable_password_filling` | 没有能单独关掉密码填充的参数；要关请用「禁用保存密码」 | `30-` §3 同节（排除 `pwd_fill` 扩展 + 跳过密码清单任务，两者本版都没有） |
| 归类 | `sync_password`、`fb_cloud_password_manager` | 没有云端同步，也就没有同步密码 | `30-` §9 |
| 时代变了 | `flash` | Chrome 早已不再支持 Flash，没有可开关的 Flash | 内核 157 无 Flash |
| 值域唯一 | `browser` | 只有 Chrome 内核（Firefox 不支持），固定为 Chrome | 字段表 `values: ["chrome"]` |
| 语义重叠 | `tabs`、`open_tabs`、`new_startup_page` | 打开哪些页面只看「启动打开的网址」 | `src/runtime/manager.js` 只读 `open_urls`（CEO 裁定：不自己发明语义） |

## 4. 位置错了的：`sync_*` 挪栏（不是禁用就完事）

## 6. `win_x` / `win_y` 的联动禁用（用户能感知的那一条）

对手：`win_x/win_y` **只在 `window_position === "topLeft"` 时才被推给内核**（`30-` §7）。
所以「填了 `win_x=800`，但窗口位置是 maximize」= 数字被静默忽略 —— 这正是「假字段感」的来源。

我们的做法（**比对手好**，不是复刻）：`window_position` 不是 `topLeft`（留空按对手默认=topLeft）时，
这两个输入框**直接禁用**，旁边一行「当前不生效 · 当前「窗口位置」是 maximize，这两个坐标不会被使用；
要按坐标摆放，请把窗口位置改成 topLeft」。改了 `window_position` 会立刻重画这一栏（不丢焦点：监听 `change`
而不是 `input`）。

代码侧同样按 `topLeft` 门控，两处故意与对手不同（写在 `chrome.js` 注释里）：

1. 两个数都必须是**有限整数**才发（对手 `winX||0` 会把没填的当 0）；
2. 不照抄兜底分支 `--window-position=0,0`（那会把窗口钉在左上角、可能被任务栏压住）——
   其它取值我们什么都不加，让窗口管理器自己摆。

## 7. 已知缺陷 / 我没验的部分（不许读成已验证）

1. **`npm run smoke` 这一版没有整条跑**（需要真内核与单租户窗口，团队规矩：谁要跑先经 CEO 排窗口）。
   本版跑了 `npm test`（25 个脚本、全离线）+ **两条新增的 B 层真内核判据各自单独跑过**
   （`close-purge-kernel` 16 PASS / `login-cookie-kernel` 19 PASS，内核 157.0.8103.78）。
   `switches.test.mjs` 的 `disable_video` 读数**没有重跑**，引的是既有读数。
2. **`cookie` 现在有真内核读数了**：`test/login-cookie-kernel.test.mjs` 在真内核上验了「页面
   `document.cookie` 里有它 / 对照组没有 / 乱码不锁死环境 / 原始串按启动网址挂上」。
   仍然没验的：`httpOnly` / `secure` / 分区 cookie 在**启动写入**这条路上的表现（它们由
   `writeCookies` 统一处理，导入接口有覆盖，但启动这条路只验了普通 cookie）。
3. **`clear_cache_after_closing` 删的是整个 `userdata`**（cache + cookie + localStorage + 书签），
   与对手删整个 `cacheFloder` 同范围 —— 但后果比「清缓存」三个字重：**登录态只有 `cookie` 字段里
   存着的那些会被写回**，浏览器里现登的会丢。界面上那一项的 hint 已写明。
   「删失败只记日志」照抄对手的静默语义，所以**用户看不到失败**——这是刻意对齐，不是漏做；
   0.4.7 的「不可逆与丢数据兜底」应该给它加一条更显眼的提示。
   **真删已验**（`close-purge-kernel`：正例删干净、对照不删、1 秒时还在证明 2 秒延迟、父目录不动）。
4. **`hidden_notification` 只在主帧注入**（与对手的 `evaluateOnNewDocument` 同覆盖面）。
   Web Worker 里 `Notification` 的可用性因内核而异，本版不额外处理，也未实测。
5. **云端 14 项与 57 项「本版做不到」仍然能被 API 写入并落库**（字段映射不变，导入导出不受影响）——
   它们只是不改变浏览器行为。这是有意选择：让脚本/导入文件的原样透传不报错。
6. 判据 A 的读取点判定是**正则在去注释后的源码上找 `.字段名`**，它挡得住「零读取」，
   但挡不住「读了却接错层」（例如读了但没往下传）。语义级数据流分析我们没做，也不假装做了。
7. 判据 D 只查 `overrides.mjs` 的**顶层键**。嵌套对象里同名键（比如两个不同字段的 `sites`）
   是正常的，不算重复；但如果哪天有人在嵌套层写了重复键，这条判据看不见。
8. 真窗口（Electron 壳）在本机 agent shell 里起不来（`0x80000003`），所以**界面上的观感**
   （「本版不支持」那行小字、页顶汇总、`win_x/win_y` 联动禁用的即时重绘）只有静态判据与
   源码级证据，**没有截图**。这属于 CEO 那边真机复验的范围。
