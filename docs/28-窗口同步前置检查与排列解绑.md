# 窗口同步：前置检查、会话日志、排列/显示解绑（0.4.7.4）

> 两件事：① 用户报「同步没反应」——真相是他那 3 个环境全停在 Chrome 错误页（代理挂），
> 主窗口上没有可捕获的页面；② 用户按 AdsPower 的习惯「勾选环境 → 窗口排列 → 启动同步」，
> 结果排列直接吃 100002。

## 1. 「同步没反应」的真相

`npm run test:sync-kernel` 在本轮之前就是 39/39 全过（键鼠/滚轮/输入框/OOPIF/teardown 都真落进受控窗口），
所以**引擎没坏**。坏的是入口：主窗口停在 `chrome-error://` 时，会话照样起起来，
binding 装上了、`Page.frameNavigated` 也挂了，但页面上永远不会有人按键 → **一条事件都抓不到**，
日志里干干净净，用户看到的就是「没反应」。

### 修法：`startSync` 前置检查（`src/sync/session.js` 的 `unusableMasterPage`）

在装 binding / 捕获脚本**之前**判主窗口这张页面能不能同步：

| 主窗口地址 | 结论 |
|---|---|
| `chrome-error://…` | 不能：「主窗口停在 Chrome 错误页（…）」 |
| `devtools://…` | 不能：「主窗口是开发者工具页」 |
| `chrome://` / `chrome-extension://` / `view-source:` / … | 不能：「主窗口是浏览器内部页面」 |
| `about:blank` 且注入脚本跑过（有派生标记） | 能（新建标签的常态） |
| `about:blank` 且没注入 | 不能：「主窗口还停在空白页，而且注入脚本没装上」 |

报错形状：`Error` 带 `reason='master_not_syncable'` + `master_url`，
文案「主窗口现在没有可同步的页面（…），先把页面打开再开始同步」；
路由层包成 `100002`。**不许起一个抓不到事件的死会话。**

**判据为什么第一版假绿**：`Target.getTargets` 在错误页上报的是「当初想去的地址」
（`http://127.0.0.1:1/nope`），页面实际停在 `chrome-error://chromewebdata/`。
现在读的是**页面自己的 `location.href`**（`Runtime.evaluate`）。

### 会话日志（用主窗口 profile 的实例日志，用户说「没反应」时能直接定责）

- 开始：`同步开始 会话=xxxxxxxx 主=<id> 受控=<ids> 主窗口=<url> 捕获脚本=已装 binding=<name>`
- 结束：`同步结束 会话=… 事件=N 转发=N 开关拦下=N 文本发出=N 文本被吞=N teardown=binding 已摘/未摘（原因）`
- 异常结束：`同步异常结束 … teardown=binding 未摘（连接已断）`

`转发` 是「真的排进 ≥1 个受控窗口的事件数」，与「被开关拦下」分开记。

### 读数（`npm run test:sync-kernel`，49/49 通过）

- 日志：`同步开始` 带主窗口 url 与 `捕获脚本=已装`；`同步结束` 带
  `转发=\d+ 开关拦下=\d+ teardown=binding 已摘`。
- 错误页红测：前置 `chrome-error://chromewebdata/`；`startSync` 抛
  「主窗口现在没有可同步的页面（主窗口停在 Chrome 错误页（chrome-error://chromewebdata/）），先把页面打开再开始同步」；
  `reason=master_not_syncable`；`running=false`；错误页里无 binding 残留 `[]`；日志有「同步未开始」。
- 异常结束仍如实记 `removed:false + reason=connection_lost`。

## 2. 排列 / 显示 / 统一尺寸与同步会话解绑

用户实测（0.4.7.2、端口 53380）：

```
POST /api/v2/sync/arrange {"auto":true} → {"code":100002,"msg":"没有正在运行的同步会话"}
POST /api/v2/sync/show {}               → 同上
```

代码落点：`arrangeWindows` / `forceShowWindows` / `showWindows` / `unifySize` 里都是
无条件的 `if (!current) throw`。而对手的正常流程是**排列不需要同步已经起来**，
界面上「窗口排列」区块就在那里、点了就报错。

### 修法（`resolveWindows`，一处解析、四个动作共用）

| 入参 | 行为 |
|---|---|
| 没给 ids + 有会话 | **与解绑前完全一致**：用会话里的 targets（`source='session'`，不重复 attach） |
| 给了 ids | 会话里已有的**直接复用**；其余用 `getInstance(id)` 已连的浏览器级 CDP 客户端（`source='ids'`） |
| 没给 ids + 没会话 | `100002`：「没有可排列的窗口：先勾选正在运行的环境（同步没开始时也能排列），或者先开始同步」 |

硬约束：

- **不新起内核、不 `startProfile`、不重连**（静态判据钉住：四个函数体里没有
  `startProfile|launchChrome|spawn(|connectInstance(`）；
- 窗口位置尺寸是**浏览器级命令**（`Browser.getWindowForTarget` / `setWindowBounds`），
  排列一次 attach 都不产生 → 响应里 `attached: 0`，所以不存在「第二次 attach」；
- `show` 的 `page_only` 分支要 Page 域，才**按需 attach**，用完 `Target.detachFromTarget` 摘掉；
- 不在运行的环境进 `skipped` 并带原因，不静默当成功；一个都没剩下才报错。

`unifySize` 解绑后**参考窗口 = ids 的第一个**（会话路径仍是主窗口，且主窗口连接不在时
仍报「主窗口连接已不在」，不拿受控窗口顶替）。

### 界面（两页同源，不各写一套）

`web/sync-widgets.js` 的排列区块与显示区块各加一个「作用范围」：

- **已选环境**（默认）：把页面上勾选的主窗口 + 受控窗口 id 发过去（`ids`），同步没开始也能用；
- **当前同步会话**：不传 ids，用会话里的窗口（老行为）。

「窗口同步」页（`web/pages/sync.js`）与操作台（`web/pages/sync-panel.js`）各自提供
`getSelectionIds()`，组件本身不猜。

## 3. 已知限制

- 解绑路径按 id 动窗口，**角色只是标签**（`window`）；主/受控语义只有会话里才有。
- 排列**只改窗口外框**，不改视口；视口差异由 `status.size_mismatch`（>2%）提示。
- `arrange` 的 `attached=0` 是「这一轮为排列新开的 CDP 会话数」；`show` 在
  `page_only` 那批会按需 attach 一次，`attached` 会 >0（用完已摘）。
