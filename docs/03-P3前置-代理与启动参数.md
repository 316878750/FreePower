## 1. 三层 fail-closed

「不静默直连」不是一个开关能保证的，拆成三层，任何一层单独失效都还有下一层。

### 第一层：启动前预检（唯一能保证「零对外连接」的一层）

`src/proxy/probe.js` · `checkProxy()`

用**环境自己的协议/账号密码**连代理，并通过它请求出口信息接口。

- 成功 → 拿到出口 IP / 国家 / 城市 / 时区 / ISP，继续启动；
- 失败 → 抛 `800003`，`reason=proxy_unreachable`，附完整诊断（每个探测端点的失败原因）；
- 关键：这一步发生在 `spawn` 之前。所以「代理坏了」的情况下**内核进程根本没被创建**，也就不存在「先连一下再回退」的可能。

死代理实测报文：

```json
{"code":800003,"msg":"start failed: 代理不可用，已阻止启动（fail-closed）：代理不可用：http://127.0.0.1:PORT/exit → 连接 127.0.0.1:PORT 失败：ECONNREFUSED | https://ipinfo.io/json → 连接 127.0.0.1:PORT 失败：ECONNREFUSED","data":{"reason":"proxy_unreachable","proxy_check":{"ok":false,...}}}
```

### 第二层：浏览器侧只认这一个代理

`src/kernel/chrome.js` · `buildArgs()`

- `--proxy-server=<scheme>://host:port`（http / https / socks5）
- **`--proxy-bypass-list=<-loopback>`**：`<-loopback>` 是 Chromium 的「减掉 loopback 隐含绕过」写法。不加它，浏览器仍然可以直连 `127.0.0.1` / `localhost`，这是很多指纹浏览器漏掉的口子。
- 绑了代理时，用户 `launch_args` 里的 `--proxy-bypass-list` 一律拒绝（理由写进 `launch_args.rejected`），否则等于给直连开后门。
- `--proxy-server` / `--proxy-pac-url` / `--proxy-auto-detect` 在保护名单里，用户改不了。

DNS 泄漏说明：明文目标走 HTTP absolute-form，Chrome 把 hostname 交给代理解析，本机不做目标域名解析；SOCKS5 也是代理侧解析。所以不需要 `--host-resolver-rules` 全域锁死（那会连带影响 CDP 回环地址，风险大于收益）。

### 第三层：启动后出口校验

`src/proxy/egress.js` · `probeEgressInBrowser()`

开一张临时标签（走同一套注入与代理链路）请求出口接口，读完 JSON 立刻关掉。

校验两件事：

1. **浏览器出口 IP vs 预检出口 IP**：不一致 → 告警。轮换代理（每条连接换 IP）属正常形态，所以只告警不阻断；固定代理不一致则说明流量没走代理。
2. **出口地理 vs 环境声明**（`checkEgress`，见 §3）。

出口探测失败（接口被墙、被代理拦）→ 只告警，不影响启动；端点可用 `FREEPOWER_EGRESS_PROBE` 换掉。

## 2. 代理预检实现细节

| 协议 | 明文目标 | HTTPS 目标 | 认证 |
|---|---|---|---|
| `http` | absolute-form `GET http://host/path` | `CONNECT host:443` + TLS | `Proxy-Authorization: Basic`（407 → 判失败） |
| `https` | absolute-form over TLS | 暂不支持（TLS in TLS），明确报错 | 同上 |
| `socks5` | 手写握手 → 隧道 → origin-form | 隧道 + TLS | 无认证 / 用户名密码（0x02） |
| `socks4` | — | — | 明确报「不支持」，不静默降级 |

- 零第三方依赖：HTTP 分块/长度读取、SOCKS5 握手都是自写（`src/proxy/probe.js`）。
- 探测端点：默认 `http://ip-api.com/json/`（明文，CONNECT 受限的代理也能过），备用 `https://ipinfo.io/json`。
- 超时：连接 + 首包 6s（`FREEPOWER_PROXY_TIMEOUT`），坏代理要是「快速失败」，不能拖住启动。
- 出口信息归一：`ip / country / countryCode / region / city / timezone / isp`，兼容纯文本 IP 与 `status=fail`。
- 已写回 profile 的字段：`ip` / `ip_country` / `ip_city` / `ip_region`（字段表里本来就有这四个，之前建了表没接业务）。

`bypass_proxy_check=1` 的环境会跳过预检（字段表里的原生开关），但启动响应里会挂一条显式告警。

## 3. 出口一致性与地理（全部降为 soft）

`packages/profile/src/validate.js` · `checkEgress()`

| 规则 | 级别 | 说明 |
|---|---|---|
| 声明时区 ≠ 出口时区 | soft | 「换 IP 没换时区」是被抓最常见的原因 |
| 语言国家 ≠ 出口国家 | soft | 如 `en-US` 出口在 JP |
| 出口 IP 是内网/本机 | soft | 说明根本没出去 |
| 预检 IP ≠ 浏览器 IP | soft | 轮换代理属正常；固定代理则是没走代理 |
| 未绑定代理 | soft | 「出口即本机 IP，跑真实账号请务必绑代理」 |

为什么是 soft 而不是阻断：出口只能证明「像不像同一个地方」，代理供应商轮换 IP、探测接口临时抽风都是正常情况，拿它当红灯会把可用环境全挡死。**「代理根本连不上」才是红灯，那是第一层的事。**

## 4. launch_args 白名单

`src/kernel/launch-args.js` · `mergeLaunchArgs()`

对外契约不变（v1 出站 JSON 字符串、v2 数组、内部数组），这里只决定「哪些参数真的进 argv」。

### 白名单（会合并进真实命令行）

| 参数 | 合并方式 |
|---|---|
| `--disable-features` / `--enable-features` / `--disable-blink-features` / `--enable-blink-features` | **并集**（不覆盖系统值） |
| `--load-extension` / `--disable-extensions-except` | 并集；`--load-extension` 自动补 `--disable-features=DisableLoadExtensionCommandLineSwitch`（Chrome 137+ 不加这条等于没生效） |
| `--proxy-bypass-list` | 仅**未绑代理**时可用；路径不存在/被代理锁定时回报原因 |
| `--start-maximized` | flag，去重 |

### 保护名单（一律丢弃并回报原因）

`--user-data-dir`（目录系统算）、`--remote-debugging-port` / `-pipe` / `-address`（随机端口+回读）、`--extended-parameters`（内核策略通道）、`--lang` / `--accept-lang`（环境字段决定）、`--user-agent`（CDP 覆写会盖掉）、`--proxy-server` / `--proxy-pac-url` / `--proxy-auto-detect`（fail-closed）、`--enable-automation`（`navigator.webdriver` 来源）、`--disable-gpu`（WebGL 声明会与软件渲染冲突）、`--disable-software-rasterizer`、`--headless`、`--window-size`、`--window-position`、`--profile-directory`、`--incognito`、`--disable-web-security`、`--allow-running-insecure-content`、`--ignore-certificate-errors`。

`--enable-blink-features=AutomationControlled` 单独拒绝；`--disable-blink-features=...,AutomationControlled` 里那一段会被移除并告警。

### 回报结构

```json
"launch_args": {
  "applied": ["--disable-features=SmokeProbe"],
  "rejected": [
    {"arg":"--user-data-dir=C:\\evil","reason":"环境隔离目录由系统计算，不接受覆盖"},
    {"arg":"--no-such-flag=1","reason":"不在白名单（只为确定性行为放行，见 docs/03）"}
  ]
}
```

被拒绝的参数同时进 `warnings`（`field=launch_args`），用户看得到「为什么没生效」。

## 5. UA 跟版

### 为什么要改口：目录名不是版本真值

实测抓到一次：`C:\Program Files\Google\Chrome\Application` 下同时存在 `156.0.8078.80` 和 `157.0.8103.40`，而 `Application\chrome.exe` 这个启动器实际跑的是 **156**（更新还没落地）。按目录名取最大版本会得到 157 → UA 报 157、内核真的 156，这就是最容易被抓的矛盾。

所以版本判定统一改成：**`Browser.getVersion` 返回的 `product` 才是真值**。

### 落地方式

1. `src/kernel/chrome.js`：`findChrome()` 读过 `data/kernel-version.json` 里的实测版本（`source` 会变成 `system+probe`）；没有缓存才按目录猜。
2. `src/runtime/manager.js`：启动、连上 CDP 拿到真实版本后 → `alignProfileToKernel()` 对齐 → 落库 → 用对齐后的 profile 做注入。
   - 对齐项：UA 里的 `Chrome/<major>.0.0.0`、`client_hints.ua_full_version`、`brands`、`fullVersionList`、`kernel_version` 列。
3. 每次启动成功都把真实版本写回缓存，新建环境直接用实测版本，不需要每次都「先错再对」。
4. `FREEPOWER_UA_AUTOALIGN=0` → 只告警不改数据（给「UA 要和内核刻意不一致」的高级用法留口）。

启动响应新增 `ua_aligned: {from, to, patch, reasons}`，对齐原因逐条可读：

```json
"ua_aligned": {"from":"150.0.7000.1","to":"156.0.8078.80","reasons":["UA 版本段 150.0.0.0 → 156.0.0.0","UA-CH ua_full_version 150.0.7000.1 → 156.0.8078.80","kernel_version 150.0.7000.1 → 156.0.8078.80"]}
```

## 6. 校验分级

以前「一致性告警一律当错误」，会误挡语言↔时区这种软冲突。现在分两级：

| 级别 | 规则 | 默认行为 |
|---|---|---|
| **hard** | UA 平台 ↔ `navigator.platform`；UA-CH platform ↔ platform；UA 版本 ↔ `ua_full_version`；`webgl=2` 但缺 vendor/renderer | 阻断（`800005`） |
| **soft** | 语言↔时区；核数↔内存不像真机；SwiftShader；`webrtc=proxy` 没绑代理；出口地理/时区不一致；参数被拒；未绑代理… | 只告警，照常启动 |

- `force=1`（`GET /browser/start?...&force=1`）显式越过 hard 冲突，并在 `warnings` 里写明越过了哪几条。
- **值域错误 force 也越不过去**（`webgl=9` 这种是脏数据，不是业务选择）。
- `800005` 响应的 `data.errors` 现在只含值域错误 + hard 冲突，不再把 soft 混进去。

## 7. 契约变化（都是超集，旧字段一个没动）

`browser/start` 的 `data` 新增：

| 字段 | 内容 |
|---|---|
| `proxy` | 预检结果（`ok/ip/country/countryCode/city/timezone/isp/latency_ms/proxy`）或 `null` |
| `egress` | 浏览器内出口探测结果（同上形状 + `url`）或 `null` |
| `ua_aligned` | 跟版记录，未触发为 `null` |
| `launch_args` | `{applied, rejected}` |
| `warnings` | `[{field, message, severity}]`，soft 集合 |

新端点：

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/v1/proxy/check`、`/api/v2/proxy/check` | 传入 `{proxy_config:{proxy_type,host,port,username,password}}` 或平铺字段，返回预检结果（`data.ok` 为布尔，失败也走 `code:0`，因为这是「检查结果」不是「调用失败」） |

失败路径：代理不可用时 `code=800003` + `data.reason=proxy_unreachable` + `data.proxy_check`。错误码全集没变，没有新增数字（避免客户端按 6 个码写死的分支被打散）。

## 8. 已知缺陷（不藏）

1. **轮换代理会对「出口 IP 一致」判告警**：每条连接出口不同是正常业务形态，目前只能告警不能智能识别。判断依据写在告警文案里。
2. **PAC 仍然无法 fail-closed**：`full_pac_url` 可配，但 PAC 里可能有 `DIRECT` 回退；绑代理时我们忽略它并告警，不绑代理时才用 `--proxy-pac-url`。
3. **多级代理（`is_multi_level_proxy`）未实现**：只对第一跳预检和注入，链路中间跳不可见，启动时告警。
4. **SOCKS5 账号密码只有预检支持**：Chrome 的 `--proxy-server` 不接受 SOCKS5 凭据（内核限制），绑了带密码的 SOCKS5 会在浏览器侧认证失败。HTTP/HTTPS 代理认证走 CDP `Fetch`。
5. **`https` 代理 + `https` 目标暂不支持**（TLS in TLS），预检会明确报错，不会静默降级。
6. **出口探测依赖第三方接口**：默认 `ip-api`（明文，免费档有频率限制）/ 备用 `ipinfo.io`。都不通时只告警，不影响启动；换端点用 `FREEPOWER_EGRESS_PROBE`。
7. **`webrtc=local` 时 UDP 直连仍是真实行为**：这是声明的一部分，不是 bug；`disabled` / `disable_udp` / `proxy` / `forward` 都会带 `disable_non_proxied_udp`。
8. **运行中代理掉线**：浏览器请求失败，Chrome 不会自动回退直连（没有 PAC 时不存在 DIRECT 分支），与 fail-closed 一致；但没有健康检查，不会主动关闭环境。
9. Worker / AudioWorklet 双 Realm 仍未覆盖（P2 处理，README 已知限制里保留）。

## 9. 验证

```powershell
# 不需要 Chrome
npm run test          # schema 10/10 + unit 20/20（代理预检/白名单/跟版/分级）

# 需要真实 Chrome + 完整权限（沙箱挡命名管道和进程查询）
npm run smoke         # 95/95
```

本次冒烟新增的断言（都跑在本地假代理/假出口端点上，不依赖公网）：

1. 活代理预检 `ok:true` 且出口 IP 正确；死代理 `ok:false`；密码错 407 判失败。
2. 死代理环境 `start` 返回 `800003`/`proxy_unreachable`，且进程表里**没有**该环境的 chrome 进程。
3. 绑代理环境启动后：`proxy.ip == egress.ip == 203.0.113.9`；代理日志里出现 `127.0.0.1:<echo端口>` 的请求（证明 loopback 也没绕过）；页面内独立再验一次出口 IP。
4. 出口时区/语言与声明不一致 → `warnings` 里分别出现 `timezone` / `language`。
5. `launch_args`：白名单参数出现在真实 `CommandLine` 里、系统特性仍在、`--user-data-dir=C:\evil` 不在、真实 `--user-data-dir` 是系统算的目录。
6. UA 跟版：声明 150 → 对齐到真实内核版本，UA / `kernel_version` 落库，注入 UA 同步。
