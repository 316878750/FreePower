# 19 · 大文件导入与代理类型（0.4.4，2026-11-15）

出处：用户从 AdsPower 导出环境后导入 FreePower 报错（他装的是 0.4.3）。CEO 复现出**两个真缺陷**，
其中第二个会**静默写错数据**。这份文档记修法、判据、红绿读数与剩下的边界。

用户那份文件只用来做本地验证，**没有入库、没有打印 cookie 值或代理密码**：

```
C:\Users\1\Downloads\profiles_2026_11_15_14_03_44.txt
18,884,174 B / 50 块 / 单块 cookie 行最长 559,542 字符 / 50 块全是 proxytype=socks5
```

---

## 一、缺陷 ①：2 MB 请求体上限 + 先断连接后回响应

`src/api/server.js` 原来是：

```js
const MAX_BODY = 2 * 1024 * 1024;
...
if (size > MAX_BODY) { reject(new ApiError(ERR.INVALID, 'body too large', 413)); req.destroy(); return; }
```

客户端正在上传 21 MB，服务端在收到第 2 MB 时就 `destroy()` —— 响应还没写出去，连接已经没了。
`fetch` 把这次请求当网络错误抛出，界面 `toast('导入失败：' + e.message)` 于是显示
**`导入失败：Failed to fetch`**。用户得不到任何可行动的信息，也不知道是文件太大。

**导入逻辑本身没坏**：切成 3 块（合计 1,145,291 B）后 200、`imported:3`。是「整份塞不进一个请求」。

### 四种写法的实测（Node 24 / undici fetch，body 21 MB，上限 2 MB）

| 超限时的做法 | 客户端看到 |
| --- | --- |
| 先 `reject` + `req.destroy()`（原状） | `fetch failed` |
| 只 `res.end(413)`，不管剩余请求体 | `fetch failed` |
| `res.end` 之后再 `destroy` | `fetch failed` |
| **把剩余请求体读完，`'end'` 时回 413** | **HTTP 413 + 完整 JSON** ✓ |

原因很直白：客户端还在写的时候服务端关连接，客户端把这次交换当网络错误，读不到响应。
所以「让客户端把话说完，再告诉它太大」是唯一能把 msg 送到界面上的路。

### 修法

- `MAX_BODY` 默认 **64 MB**（`MAX_BODY_DEFAULT`），`FREEPOWER_MAX_BODY`（字节）覆盖，**每次请求现读环境变量**
  （改了不用重启进程，判据里也能逐条改）。
- 超限后**不立刻断开**：丢掉已收的 chunks，继续把请求体读完，`'end'` 时回 413。只留一个极端兜底
  `MAX_DRAIN = 512 MB` —— 有人真往本机灌超过 512 MB 才主动断开。
- 413 的文案要能指导动作，带真实数字：

  ```
  请求体过大：23105049 字节，上限 2097152 字节；请分批导入
  （控制台导入 .txt 会自动分批；脚本可调 FREEPOWER_MAX_BODY 调大上限）
  ```

- 413 响应加 `connection: close`：这次请求体我们没消费完，别让客户端拿同一条连接再发。

64 MB 是**我们选的上限**（一份 50 块导出文件约 21 MB × 3 倍余量），不是「协议上限」，超了照样明确 413。

## 二、缺陷 ②：`proxytype=socks5` 被存成 `http`（静默写错，最严重）

`src/store/transfer.js` 的 `proxyOf` 原来是：

```js
return {
  proxy: {
    proxy_type: item.proxy_type || item.proxytype || fromString.proxy_type,
    proxy_soft: item.proxy_soft,
    ...fromString,          // ← 展开写在后面
  },
};
```

`parseProxyString` 返回的对象里带 `proxy_type: scheme || undefined`。展开在**后面**，
把前面算好的 `'socks5'` **覆盖成 `undefined`**，`normalizeProxy` 再兜底成 `'http'`。

结果：用户 50 个环境全按 http 去连（`host` / `port` / 账号密码都在，只有类型错），**一句告警都没有**。
这是最难查的一类错 —— 看起来导入成功，实际连不上或行为不对。

### 修法（两处，缺一不可）

1. **根因去掉**：`parseProxyString` 不再产出 `proxy_type` 键，改成返回 `scheme`（`''` 表示没有前缀）。
   「谁的优先级高」只在一个地方决定，不在两层各算一次。
2. **顺序钉死**：`proxyOf` 里先 `const { scheme, ...conn } = fromString;` 再 `{ ...conn, proxy_type: 显式值 || scheme || undefined }`
   —— 先展开、后写显式值。以后谁往 `conn` 里加字段，也不会再覆盖掉算好的值。

优先级：顶层显式 `proxy_type` > AdsPower 的 `proxytype` > 字符串里的 `socks5://` 前缀 > 无（→ 兜底 `http`，既有语义不变）。

### 顺带核过的同类写法

- `proxy_soft`：`item.proxy_soft` 在展开之后，且 `fromString` 里没有这个键 —— 不会被覆盖，保持原样。
- `proxy_id`：不在 txt 字段表里、又属于 `STRUCTURAL`，txt 的 `proxyid` 会被忽略（不会误当成本机代理引用）—— 行为正确，不动。

## 三、界面：`.txt` 分批（用户真正走的那条路）

只把服务端上限提到 64 MB 还不够 —— 让一个大文件依赖「上限刚好够大」是脆的，而且分批之后进度、
失败定位都更清楚。所以控制台这一侧**按块分批**，切块逻辑抽成纯函数 `web/txt-split.js`：

- `splitTxtChunks(text, {maxBytes, maxBlocks})` → `{chunks, total_blocks, total_bytes}`
- `countTxtBlocks(text)`：与 `src/store/adspower-txt.js` 的 `parseBlocks` **同一口径**（一行 ≥10 个星号是块尾，
  末尾残留那段算一块）。
- `mergeBatchResults(chunks, results)`：把每批的 `failed[].index`（**批内**序号）换算成整份文件的块号。

### 三条硬规矩

1. **只在块边界切**，绝不切在 `cookie=` 行中间（那一行可以 50 万字符）。
2. **双阈值**：每批 ≤8 MB 字节 **且** ≤40 块，谁先到就切。8 MB 是给服务端 64 MB 留余量，
   40 块是防「很多小块的导出」把请求数打爆。
3. **所有批次拼起来逐字节等于原文**（不 trim、不改换行、不补 BOM）。这条既是判据，
   也是「分批无损」的唯一理由。

拼不回去 = 说明切块把某个块切坏了，那就等于静默丢数据。

### 界面行为

- 顺序发送、进度常驻（新增 `ui.progressToast`，不是会自己消失的 toast）：
  `正在导入 12/50 块…（第 3/5 批）`。
- **一批失败不中断**：记下这一批覆盖的块号范围（`第 3 批（第 17–24 块）整批失败：<原因>`），继续下一批。
- **失败项的块号换算**：服务端返回的 `index` 是「本请求内第几块（0 基）」，界面加 `first_block`。
  不换算是分批导入最容易错的点：每批都「第 2 块失败」会全显示成「第 2 块」。
- 服务端每批响应新增 `blocks`（本请求解析出的块数）。与界面预期不一致时进 `warnings`：
  「服务端解析出 99 块、预期 40 块，失败清单里的块号可能偏移」—— 宁可不说话，也不让用户拿一份错位的清单。
- 服务端 `failed[].index` 一律是**块号**：`parseAdspowerTxt` 新增 `itemBlockIndex`，`importProfiles` 支持
  `indexOf` 换算（缺 `name` 的块没进 items，项号 ≠ 块号，不换算就会指错块）。
- **网络层失败给中文**：`web/api.js` 的 `call()` 捕获后包装成 `FpError`，不再把 `Failed to fetch` 冒泡给界面；
  原始错误只进 `console.warn`（排障用）。

## 四、判据

### A 层（不碰 Chrome，进 `npm run test:api`）：`test/api.test.mjs` 新增 20 条

- `proxytype=socks5` → `proxy_config.proxy_type === 'socks5'`、`https → https`、缺省 → `http`；
  再加一条「显式 `proxytype` 优先于字符串里的 `socks5://` 前缀」。
- 切块纯函数：默认阈值（8 MB / 40 块）、字节上限、块数上限、三种配置下拼回逐字节等于原文、
  每批以整块结尾（没切在 `cookie=` 行中间）、`first_block` 连续累加、`countTxtBlocks` 与服务端口径一致、
  单块超阈值时单独成批并标 `oversized`（不切碎块）、空文件不产生批次。
- 汇总：批内 index 换算成整份文件的块号、`imported` 是各批之和、整批失败不中断且点名块号范围、
  服务端块数与预期不符时出声。

### B 层（真 HTTP 端到端，进 `npm run smoke`）：`test/import-large.test.mjs` 15 条

合成 **18.9 MB / 50 块 / 最大 cookie 行约 50 万字符**（与用户那份同阶，cookie 全是合成假串），

## 五、边界（写清，别当成已解决）

1. **64 MB 是我们选的上限**，`FREEPOWER_MAX_BODY` 可调。单次请求装的块数上限仍是 **1000 条**（未改）。
2. **超限时要先把请求体读完再回 413**，代价是那只连接要陪着收完这几 MB。极端情况（>512 MB）才主动断开，
   那种情况客户端仍可能拿到网络错误 —— 这是有意的兜底，不是遗漏。
3. **界面分批是顺序发**（每批一次 POST；这份 18.9 MB / 50 块按默认阈值只切 3 批）。
   中途关页面 = 剩余批不会发；已成功的批已落库（不回滚），重试会重复建环境 —— 导入**不是**幂等的。
4. **不做流式解析**：整份文件先读进内存再切块。18.9 MB 没问题；几百 MB 的文件会吃内存（浏览器侧）。
5. **0.4.3 已经写错的数据不会自动修**：0.4.3 导入的 `socks5` 环境在库里是 `http`。
   用户在 0.4.3 里成功导入过的环境，需要重导或手工改代理类型。用户这次整份导入失败（连接被掐、一条没进库），
   所以没有受影响的数据 —— 但这条对其它用户是真事，升级说明里要写。
6. **本次不动数据库结构**（无新列、无新表）→ 0.4.4 ↔ 0.4.3 可以互相打开同一个库。
7. 用户的真实导出文件**不进测试、不进仓库**（含 cookie 值与代理密码）。B 层用合成数据。
