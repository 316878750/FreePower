# 29 - 窗口同步规格（按 AdsPower 8.9.23 实测行为对齐）

> **后续**：根因定位与修复（后台节流 / iframe 捕获 / Win32 鼠标投递）及判据读数见 `30-窗口同步修复-后台节流-iframe-Win32投递.md`。
> 依据：`adspower-reverse/8.9.23/34-窗口同步真实行为.md`（2026-11-21 实测，五问全部有证据）
> 目标版本：0.4.7.11
> 本文是**行为规格**，不是实现方案。实现可以不同，行为必须对得上。
> 用户对同步的定义（原话）：「同步是指主控窗口任何操作，其它窗口都跟着一起操作。」

---

## 0. 为什么要有这份文档

0.4.7.9 与 0.4.7.10 两版都没解决「主控操作、其它窗口不动」。实测证据已经指出根因方向：

**AdsPower 的投递对象是「窗口句柄」，没有 target 这个概念。** 事件交给窗口，由窗口决定进哪个标签，所以切标签、关标签、开新标签全都即时跟上。我们的实现是「会话启动时解析一个 CDP target 并绑死」，target 一旦被替换或销毁，整条链路静默失效。

这与 0.4.7.10 现场完全吻合：主控 `target_id=DB4B3123AD` 在会话中途从窗口的 target 列表里消失，而 `sync/status` 仍报 `running=true`、`visible=true`、`confident=true`。**状态在说谎，所以没人发现它已经死了。**

结论：不改用 OS 钩子（2026-11-14 已定：全局钩子有隐私风险，且 `LowLevelHooksTimeout` 会静默摘钩——34 号文 §8 恰好实测到了 AdsPower 自己间歇性停转发）。**继续用 CDP，但把「target 语义」换成「窗口语义」。**

## 1. 实测事实 → 规格条目

证据等级沿用 34 号文：【实】=直接读到，推断=与观测一致，未测=本轮没测。

### R1 捕获必须覆盖主控窗口内**所有** page target【实 · 对应 §2.3 §3.1–§3.4】

- 实测：AdsPower 捕获在 OS 层，与标签无关；切标签后事件进新标签（A3=5/A1=0 → A1=1/A3=0 → 回 A3）。
- 规格：会话启动时，对主控窗口 CDP endpoint 的**全部 page target** 逐个 attach 并注入捕获；运行中订阅 `Target.setDiscoverTargets`，`targetCreated` 立即注入、`targetDestroyed` 立即移除。
- 不要求判断「谁可见」：只有真正接收输入的标签才会产生页面事件，**全装 = 天然跟随激活标签**。
- 禁止：启动时只选一个 target 并长期绑定。

### R2 转发目标必须在**发送时**解析【实 · 对应 §3.1–§3.4】

- 实测：受控窗口切标签、关当前标签回落、新开标签，事件都立刻改投新的激活标签，同一次会话内不需要重启同步。
- 规格：每个事件派发前解析该受控窗口的**当前激活 page target**；允许 ≤500ms 短缓存，但任何 `targetCreated/targetDestroyed/targetInfoChanged` 必须立刻失效缓存。
- 解析不到可用 target → 本轮跳过该窗口并记 `skipped_no_target`，**不许静默**。

### R3 坐标：客户区 1:1、不缩放、越界丢弃【实 · 对应 §5.1 §5.2】

- 实测：主控 `clientX=246/446/646`，受控 `clientX` 完全相同；受控窗口只有主控 1.6 倍尺寸差也不缩放。
- 实测：主控 `clientX≈900/clientY≈900`（仍在主控视口内），受控视口约 684×779，**一条都没收到**——越界直接丢，不 clamp、不缩放。
- 规格：直接用主控事件的 `clientX/clientY` 原值派发；派发前取受控页 `innerWidth/innerHeight`，越界丢弃并计数 `dropped_out_of_view`。

### R4 操作覆盖范围【实 · 对应 §6】

必须覆盖：`mousemove`、`mousedown`、`mouseup`、`click`、`wheel`、`keydown`、`keyup`。

- 键盘按 `key/code/keyCode` 三件套原样转发（实测受控侧 `key=b / code=KeyB / keyCode=66` 完全相同）。
- `wheel` 按 `deltaY` 原值转发（实测两侧都被 Chromium 归一成 100）。
- **第一次点击就必须投递**：实测「不存在首次点击被激活吞掉」。禁止「先 bringToFront 再投递」这类两次派发，禁止丢第一个 `mousedown`。

### R5 状态必须自证，不许再说谎【本轮新增 · 针对 0.4.7.10 的实际失败】

`GET /api/v2/sync/status` 必须能回答「它现在到底还活着吗」：

| 字段 | 含义 |
|---|---|
| `alive` | 捕获脚本是否真的装在 ≥1 个 target 上（读页面 marker 得到，不是看进程在不在） |
| `targets_attached` | 当前挂了捕获的 target 数 |
| `last_capture_target_url` | 最近一次真正产生事件的那个 target 的 URL |
| `events_from_current_target` | 当前 target 上的事件数（不是全会话累计） |
| `last_event_at` / `stale_ms` | 最近事件时间与距今毫秒 |
| `windows[].delivery_target_url` | 最近一次实际投递到的受控 target URL |
| `windows[].delivery_ok` / `skipped_no_target` / `dropped_out_of_view` | 每窗口投递计数 |

探针：`POST /api/v2/sync/selftest` 返回每个受控窗口与其当前 target 的 `{targetId, url, visibilityState, capture_installed}`。捕获脚本在页面里留一个 `window.__fpSyncProbe`，用它证明「脚本真的在这个页上」。

### R6 看门狗：静默失效必须自愈【实测依据：34 号文 §8】

- 实测：AdsPower 自己也会「worker 活着、状态仍是同步中、转发停了」，t+33s 收到 0 条、t+63s 自己恢复。
- 规格：`running` 且 `events` 连续 60s 无增长 → 自动重装捕获（重新 attach 全部 target + 注入），记 `capture_reinstalled` 计数并在状态里体现。
- 目的：即使出现同类静默失效，也不许要用户手动重启同步。

### R7 受控页 `document.hasFocus()` 为 true【实 · 对应 §7.4】

- 实测：受控窗口不是前台时，受控页 `hasFocus()` 仍返回 true（`PostMessage` 路线的副作用）。
- 规格：受控 target attach 后启用 `Emulation.setFocusEmulationEnabled({enabled:true})`，让依赖 focus 的页面（懒加载、快捷键、输入框）行为对齐。
- 理由：很多站点靠 `hasFocus` 决定是否响应键盘/滚动，不补这条会出现「事件到了但页面不响应」。

### R8 主控选取规则【推断 · 对应 §4】

- 实测：主控 = 句柄串第一个；反序勾选后顺序不变 → 更像列表行序/句柄序，不是勾选顺序（两者本轮无法区分，标推断）。
- **决定：保持 FreePower 现有规则（勾选顺序第一个为主控），界面必须明确标出「主控」。** 理由：实测本身是推断，未区分；「第一个勾的当主控」更符合直觉，且界面标注后不产生操作习惯落差。
- 记为已知差异，不阻塞交付。

## 2. 已知差异（诚实列出，不假装对齐）

| 项 | AdsPower 实测 | FreePower 规格 | 处理 |
|---|---|---|---|
| 受控侧 `mousemove.buttons` | 恒为 1（悬停与拖拽不可区分） | CDP 按真实按键状态填，悬停=0 | **不复刻这个 bug** |
| 浏览器 chrome 区域操作（地址栏/标签栏） | OS 钩子能捕 | 页面 JS 捕不到 | 已知限制，写进文档 |
| 受控窗口最小化 | 完全停止投递 | CDP 仍可能投递 | 不强制停止，只记 `window_minimized` |

| 注入痕迹 | `isTrusted=true` + `buttons=1` | `isTrusted=true` | 无法完全一致 |

## 3. 判据要求（先红后绿，缺一不算）

**硬规则：任何判据不许把 `scheduler.sent > 0` 或 `errors === 0` 当作通过条件。** 0.4.7.9 就是 `sent=311 / errors=0` 全绿而用户看到不动。

必须有的判据，每条都要先证明它在旧实现上变红：

1. **C1 切标签**：受控窗口切到另一标签后，事件改投新标签，旧标签归零。
2. **C2 关标签/开标签**：关掉受控当前标签后照投回落标签；新开标签后照投新标签。
3. **C3 主控 target 被替换**（导航/关标签/新开）后捕获不丢——这是 0.4.7.10 的真实失败场景，必须能抓住。
4. **C4 坐标**：1:1 同值；越界丢弃（不 clamp、不缩放）。
5. **C5 端到端像素**：真内核 + 两个真实窗口 + **真实 OS 鼠标**（SendInput）滚动主控可见页 → 受控窗口页面截图**前后像素差 > 阈值**。像素没变即失败。
6. **C6 状态自证**：故意不注入捕获脚本 → `alive=false`，而不是 `running=true`。反向验证：注入后 `alive=true`。

C5 由 CEO 独立复跑，不采信开发自报读数。
