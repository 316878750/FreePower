# P1 窗口同步（Synchronizer）方案

> 状态：**方案待 CEO 审**（2026-11-14）。本文件只有设计，没有实现代码。
> 目标：对齐 AdsPower Synchronizer 的**能力面**，自己实现，不搬它的代码与素材。
> 范围约束：只支持 Chromium 内核（我们只有 CfT Chrome，天然满足）；Windows 目标平台；**不做 RPA**。

## 一、能力清单 → 我们要做什么

对手的入口两个、概念三样。逐条对应到我们的实现：

| 对手的能力 | 我们的做法 | 阶段 |
|---|---|---|
| 列表选中 ≥2 个环境点「开始同步」 | 环境列表工具条加按钮，只在「勾选 ≥2 且都在运行」时可用 | 1 |
| 独立的「窗口同步」页 / 控制台小部件 | Electron 再开一个小窗（`alwaysOnTop`、无边框、可移动），加载同一套控制台的 `#/sync-panel` | 1 |
| 主窗口 / 受控窗口 | 会话里存 `masterId` + `slaveIds[]`，全部为**运行中**的环境 | 1 |
| 键盘 / 鼠标同步开关（输入、点击、滚动、移动） | 四个独立开关，任一类关掉就不转发该类事件 | 1 |
| 文本：清空 / 粘贴 / 指定文本（按行，顺序或随机）/ 相同文本（可模拟人工输入）/ 随机数字（范围） | 服务端生成文本 → `Input.insertText`，逐字带延迟（模拟人工）；顺序/随机由种子化 RNG 决定 | 1 |
| 标签：同步所有标签 / 关当前 / 关其他 / 关空白 / 访问指定网站（当前标签或新标签） | `Target.*`（见 Q3） | 2 |
| 窗口：网格/重叠、置前、统一尺寸、自定义位置与间距、指定主窗口、按分组过滤、多屏 | CDP `Browser.setWindowBounds` + Electron `screen`（见 Q4） | 3 |
| 主题色 / 快捷键 Ctrl+Alt+S | 面板内主题色（CSS 变量）+ Electron `globalShortcut` | 3 |
| 点击延迟 / 打字延迟 | 主进程调度（见 Q5） | 1 |

**明确的边界（不冒充）**：

- 只同步**页面内容区**的输入。浏览器自带的地址栏、书签栏、标签栏、右键菜单**不同步** —— 那不是 CDP 能碰的地方。
- 主窗口失去焦点时没有输入可捕获，受控窗口也不动。这是语义，不是缺陷。
- 输入法（IME）组合过程**不能逐字重放**：组合结束后用 `Input.insertText` 一次性投递最终文本，中文输入在受控窗口里是「整段出现」而不是「逐字出现」。
- 受控窗口里 CDP 派发的事件对页面来说是 `isTrusted=true`（CDP 的 Input 域走浏览器内部），这点和「页面自己 dispatchEvent」不同 —— 是我们的优势，如实写在这里。

## 二、要审的六个问题

### Q1 主窗口的输入怎么捕获？

**结论：注入脚本 + `Runtime.addBinding` 回传，不碰 OS 钩子。**

CDP 的 `Input` 域只能发、不能收，所以捕获必须在页面侧。做法：

1. 主窗口每个执行上下文里 `Runtime.addBinding({ name: '__fpSyncSend' })`，然后注入一段捕获脚本
   （`Page.addScriptToEvaluateOnNewDocument` 保证导航后仍有 + `Runtime.evaluate` 补当前文档）。
2. 脚本在 **window capture 阶段**监听 `mousemove` / `mousedown` / `mouseup` / `wheel` / `keydown` / `keyup` / `compositionend`，
   **只上报事实**：事件类型、按钮、按键三元组（`key` / `code` / `keyCode`）、修饰键、滚轮增量、
   归一化坐标 `x/innerWidth`、`y/innerHeight`、时间戳。
3. 每批事件 `JSON.stringify` 一次投给 `window.__fpSyncSend(...)`；主进程从 `Runtime.bindingCalled` 收到。

为什么不用 OS 级钩子（`WH_MOUSE_LL` / `WH_KEYBOARD_LL`）：那要 ffi 依赖、要拿到屏幕坐标再翻译回「哪个窗口的哪个 DOM 位置」，还要处理 DPI 缩放；
而且我们看到的是坐标，不是页面元素 —— 页面侧捕获反而更准（直接就是 CSS px 与视口比例）。

**`src/kernel/inject.js` 能不能复用？** 机制可以照抄思路（它已经在用 `Page.addScriptToEvaluateOnNewDocument`），
但**不复用那份脚本**：inject.js 是指纹注入，逐帧、跨 worker、和 `seeds` 绑定，混进同步逻辑会让两个功能的回归互相牵连。
新开 `src/sync/agent-script.js`（页面侧捕获脚本，纯字符串导出，便于单测断言「没有外链、没有 eval」）。

**页面能不能把事件吞掉？** 我们的监听器是 `addScriptToEvaluateOnNewDocument` 在 document 开始时注册的，
同 phase 下按注册顺序触发，所以比页面自己的 capture 监听更早。页面 `preventDefault` 不影响我们收到事件；
`stopImmediatePropagation` 只能拦住注册更晚的监听器。这类站点（视频站、地图）因此也能同步。

### Q2 坐标怎么映射？

**结论：按视口比例映射，不按绝对像素，也不缩放 wheel 增量。**

- 主窗口侧：`nx = clientX / innerWidth`、`ny = clientY / innerHeight`（`0..1`，超界钳到 `0..1`）。
- 受控窗口侧：`x = round(nx * vw)`、`y = round(ny * vh)`，`vw/vh` 来自该环境当前的 `Page.getLayoutMetrics`
  （`cssVisualViewport.clientWidth/clientHeight`），**每次会话开始时取一次，窗口尺寸变化时重取**。
- 两边 DPR 不同不影响：`Input.dispatchMouseEvent` 收的就是 CSS 像素。
- **点击前先发一次 `mouseMoved` 到同一坐标**：很多站点（下拉菜单、hover 才出现的按钮）只认
  `mousePressed` 前的移动序列，直接派发 `mousePressed` 会点空。这条是实测过的常见坑，写进判据。
- `wheel` 的 `deltaY` 原样转发，不按高度比例缩放：缩放会让「滚一屏」在不同窗口里滚不同距离，
  反而更难用；不同窗口可视高度不同这点由用户自己接受（面板上写明）。
- 「统一尺寸」功能打开时窗口尺寸被拉齐，比例映射退化成 1:1，不需要特殊分支。

### Q3 标签同步用什么域？

**结论：`Target.*`（浏览器级 session），配 `Page.navigate` 做「当前标签内跳转」。**

- 每个运行中的环境有一条**浏览器级** CDP 连接（`instance.wsUrl`，见 Q6），
  所以 `Target.getTargets` / `Target.createTarget` / `Target.closeTarget` / `Target.activateTarget` 直接可用。
- 「同步主窗口所有标签」：读主窗口的 page targets（按 `Target.getTargets` 的顺序），
  对每个受控环境 `Target.createTarget({ url })`，**顺序与主窗口一致**，这样后续「关闭第 N 个标签」才有稳定的序号对应。
- 「访问指定网站」：默认 `Target.createTarget({url})`（新标签）；勾了「当前标签」就对当前序号的那个 target 发
  `Page.navigate`（需要 `Target.attachToTarget({flatten:true})` 拿 session）。
- 「关闭当前标签」：主窗口当前激活的 target 在 page 列表里的**序号**，映射到受控环境同序号；受控环境标签数不够就跳过并记日志
  （不猜、不乱关）。「关闭其他」= 该序号以外的全关；「关闭空白」= `url` 为 `about:blank` 或 `chrome://newtab` 的全关。
- 防循环：所有由同步产生的导航/开标签都打 `__sync: true` 标记，不触发「主窗口变化 → 再同步」的回环。
- 所有标签操作**串行**在受控环境内部（一个环境的两次 createTarget 并发会乱序），**跨环境并发**上限 3（沿用 `BATCH_CONCURRENCY` 的思路）。

### Q4 窗口排列要 Win32，加 `koffi` 还是走 Electron？

**结论：默认零新依赖 —— 移动/改尺寸用 CDP，显示器枚举用 Electron 的 `screen`；只在「置前」验证不通过时才引 `koffi`。**

- **移动 / 改尺寸**：`Browser.getWindowForTarget({targetId})` 拿 `windowId`，再 `Browser.setWindowBounds({windowId, bounds:{left,top,width,height}})`
  （`windowState` 必须先回 `'normal'`，最大化状态下 setBounds 会被忽略 —— 这是要写进判据的坑）。
  零依赖、跨平台、给的是**外框**尺寸，正好是排列要的量。
- **多屏 / 可用工作区**：Electron 的 `screen.getAllDisplays()` 直接给每块屏的 `bounds` 与 `workArea`，零依赖。
  面板上「内置屏 / 扩展屏」分别排列 = 把窗口按顺序摊到对应 display 的 `workArea` 里。
- **置前（z-order）**：先试 `Page.bringToFront`（多数情况下 Chrome 会把自己的窗口提到前台）。
  **这一条必须实测再定**：如果实测只切标签、不抬窗口，才引 `koffi` 调 `SetForegroundWindow`。
- 如果真要引 `koffi`：MIT、预编译 N-API 二进制（win32-x64 约 2–3 MB，不需要 MSVC）、
  打包时要 `asarUnpack` 并把 `.node` 一起带出去；**加载失败必须降级**（`degraded: true` 回给界面，置前改成「尽力」），
  不能让整个同步会话因为一个问题窗口 API 起不来。
- 网格排列的数学（纯函数，可单测）：给定 N 个窗口、目标 display 的 `workArea`、行列数或「自动接近正方形」、间距 `gap`，
  算出每个窗口的 `{left, top, width, height}`；「重叠排列」= 同一原点 + 固定偏移（`offset` 累加）。

### Q5 延迟 / 随机输入在哪一层？

**结论：全在主进程（Node 侧）。页面脚本只负责「如实上报原始事件」。**

- 页面侧只转发，不解释、不延迟、不随机 —— 这样受控页面上不留任何我们的对象（页面 `window` 上只有主窗口需要一个 binding，
  受控窗口一个注入都不加，被检测面最小）。
- 主进程里的 `SyncScheduler` 负责：
  - 固定延迟 `delayMs` + 抖动 `jitterMs`（每目标独立随机，避免所有窗口同时动作像机器人）；
  - 打字延迟逐字符（「模拟人工输入」勾上时 = 每字 `min..max` 随机，没勾就是一次 `insertText` 整体投递）；
  - 点击延迟（按下与抬起之间、以及按下前的 `mouseMoved`）；
  - 文本源：按行拆分 → 顺序取 / 随机取（用种子化 RNG，种子写进会话，便于复现问题）；随机数字用 `crypto.randomInt`。
- 为什么不在页面里随机：① 页面里做延迟等于把定时器暴露给被检测的站点；② N 个受控窗口的节奏要统一调度，
  页面之间相互看不见；③ 随机源要可复现，主进程才好写判据。

### Q6 和 `manager.js` 的 CDP 连接怎么接？

**结论：每个环境**再开一条**浏览器级连接，专供同步；不复用、不共享 session。**

- `manager.js` 的 `instance` 里已经有 `wsUrl`（DevToolsActivePort 报的、浏览器级 ws）和 `port`。
  同步会话用 `CdpClient.connect(instance.wsUrl)` 新开一条，`Target.attachToTarget({flatten:true})` 按需挂到具体 page target。
- **不共用**现有的连接：现有流程开着 `Fetch.enable`（黑白名单/拦截页）、`Page.addScriptToEvaluateOnNewDocument`（指纹注入），
  再叠一层 `Target.setAutoAttach` 会互相踩（两个客户端抢 auto-attach 会让另一个收不到事件）。
  同步**只用显式 `attachToTarget`**，不碰 auto-attach，所以两边互不影响。
- 会话生命周期：`start` 时建连接 → 环境 `stop` 时（或同步 `stop` 时）`CdpClient.close()` 并清定时器；
  环境被外部杀掉 → 连接 `error/close` → 会话标 `degraded` 并从受控列表摘掉，不静默继续。
- 一条浏览器级连接上多个 page session：`CdpClient` 已支持 `sessionId`（`cdp.js:170` 的 `send(method, params, sessionId)`），
  需要补的是「按 session 分发事件」，本方案里作为第 1 阶段的第一件事（改动小、可单测）。

## 三、模块划分（实现阶段才建）

```
src/sync/session.js      会话状态机：idle → starting → running → stopping；主/从集合、降级标记
src/sync/agent-script.js 主窗口页面侧捕获脚本（字符串）
src/sync/capture.js      Runtime.addBinding + 事件解码（与 CDP 无关的纯函数：把 bindingCalled 的 payload 变成事件对象）
src/sync/replay.js       坐标映射 + CDP Input 派发（纯函数 mapPoint() 可单测）
src/sync/scheduler.js    延迟/抖动/逐字输入/顺序与随机文本/随机数字
src/sync/tabs.js         Target.* 标签同步（序号映射）
src/sync/windows.js      Browser.setWindowBounds + 网格/重叠排列数学（纯函数 layout()）
src/sync/panel.js        Electron 小窗（alwaysOnTop）+ globalShortcut
web/pages/sync.js        控制台内「窗口同步」页（环境选择、开关、文本工具、标签工具、窗口工具）
```

对外只有 Local API（界面照规矩只走 HTTP）：`/api/v2/sync/start|stop|status|settings|text|tab|arrange`。
设置存 `meta.sync_settings`（JSON），和环境数据一样留在本地。

## 四、判据（先红后绿）

**A 层（`npm test`，零 Chrome，纯函数 + 假 CDP）**

1. `layout()`：N=1/2/3/5/6、单屏与双屏、`gap` 0/8/24、重叠模式；断言窗口不越出 `workArea`、互不重叠（网格模式）、
   重叠模式的偏移严格递增。
2. `mapPoint()`：主窗口 1280×720 的 (640,360) → 受控 1920×1080 应是 (960,540)；边界 0 与 1；
   `vw=0` 时不炸（窗口最小化时 layoutMetrics 可能给 0）。
3. `Scheduler`：固定种子下「每目标随机抖动」可复现；打字延迟在 `[min,max]` 区间内；
   顺序/随机文本取行不重复（随机允许重复，但要在文档里写明）。
4. 事件解码：`bindingCalled` payload 里字段缺失/类型错 → 丢弃并计数，不抛。
5. **反向断言（防假绿）**：把坐标映射改成「绝对值直传」，第 2 条必须红；把调度器延迟设 0，「模拟人工输入」那条必须红。

**B 层（`npm run smoke`，真内核、全离线）**

6. 两个环境（本地假站），起同步 → 主窗口页面注入捕获 → 用 CDP 往主窗口 `Input.dispatchMouseEvent`/`dispatchKeyEvent`
   模拟点击与打字 → 受控窗口页面的 `input` 值里出现同样文本、`click` 计数 +1。
   **注意：不碰用户真实鼠标**（全部走 CDP 派发）。
7. 开关对照：关「键盘」→ 受控窗口不再收到按键（但鼠标仍然收到）；关「鼠标」→ 反过来。缺一个方向就是假绿。
8. 坐标对照：把两个窗口调成不同尺寸（`Browser.setWindowBounds`），点主窗口「左上角按钮」与「右下角按钮」，
   受控窗口命中的是**相同的那两个按钮**（按元素 id 断言，不按像素）。
9. 标签：主窗口开 3 个标签 → 受控环境也 3 个且顺序一致；关第 2 个 → 受控环境第 2 个关闭；「关闭其他」只剩 1 个。
10. 环境被 `stop` 后：会话标 `degraded`，再发输入不报错也不假装成功（`status` 里看得见）。
11. 无头环境 / 无窗口（CDP 拿不到 windowId）：`start` 直接失败并说清原因。

## 五、与现有代码的冲突面（提前说）

- `manager.js` 的 `stopProfile` 要**顺带关同步会话**，否则会在已死的内核上留一条 ws 连接和一堆定时器（内存泄漏 + 日志刷屏）。
- `desktop/main.js` 退出要 `globalShortcut.unregisterAll()`。
- 新增一个 Electron 小窗，`desktop.test.mjs` 里「安全姿势」那几条（`contextIsolation` / `nodeIntegration` / `sandbox`）要照同样标准配，
  不能因为是小部件就放松。
- 面板小窗加载的是同一个 `http://127.0.0.1:<port>/#/sync-panel`，所以它同样受 Origin 白名单约束，不需要新的传输通道。
