## 0. 结论先行

1. **API 契约不动**：不新增 `proxy_chain` 字段（对手没有，`20-` §1.1 三级证据），环境侧仍是 `proxy_config` 单跳 + `is_multi_level_proxy` 门控字符串。
2. **实现方式是本机中继**，不是内核 `StaticConfig.ProxyChain`：我们没有内核改造能力（`08-` §落点矩阵已定、CEO 已拍板不上内核补丁）。功能等价，形态不同。
3. **只有一处形态差异需要 CEO 拍板**：浏览器必须被告知代理，所以 argv 里必然有 `--proxy-server=http://127.0.0.1:<port>`。`20-` §4 给我们的建议判据是「启动参数里没有 `--proxy-server`」——**这条对本地中继不成立**，应改成「argv 里的 `--proxy-server` 只指向本机 loopback，上游 host/port 与凭据都不进 argv」（比对手更严，对手第二跳 host/port 是写进内核配置的）。
4. 跳数按对手结构**只做 2 跳**（`20-` §1.3：代码里只有两次 `push`），不做 N 跳。
5. 对手链不建成功时**静默退回单跳、不报错**（`20-` §3 末）；我们**显式失败**（fail-closed）。这是有意的差异，要写进 README。

## 2. 实现结构

新增 `src/proxy/chain.js`：`createChainRelay(hops) → { port, proxyUrl, close() }`

```
浏览器 --proxy-server=http://127.0.0.1:<relayPort>
   │  CONNECT host:443 / 明文 absolute-form
   ▼
[relay 127.0.0.1:<port>]  ← 只监听回环，外部不可连
   │  按 hop1 的协议转发
   ▼
hop1 环境代理（http / https / socks5，带账号密码）
   ▼
目标站点
```

要点：

1. **hop0 是我们自己的中继，不是「系统代理」**。对手 hop0 来自本机系统代理（`openSystemProxy` + `systemProxyConfig`，`20-` §1.3），我们没有系统代理这个概念 —— 这条列为不兼容项（§6）。
2. **握手代码不重写**：`src/proxy/probe.js` 里已经有 `connectTcp()`（`:108`）、SOCKS5 握手 `socks5Handshake()`（`:139`，含 0x02 用户名密码认证）、CONNECT/absolute-form 拼装（模块头 `:9-10`）。把这三个提成可复用导出，`chain.js` 只做「接浏览器 ↔ 转 hop1 ↔ 双向 pipe」。
3. **方向映射**：HTTPS 目标浏览器发 `CONNECT`，中继对 hop1 也发 `CONNECT`（http 跳）或 SOCKS5 `CONNECT`（socks5 跳）；明文 HTTP 目标浏览器发 absolute-form `GET http://…`，中继**转成 origin-form** 后经跳转发（`20-` §7 记的是我们 probe 已有的两条路径，复用即可）。
4. **凭据**：hop1 的账号密码只存在内存与中继里，**不进 argv**（`12-` §2 已实测我们现在命令行只有 `host:port`）。
5. **生命周期**：`start` 前建中继 → 探测通过 → 起内核；`stop` 时先关内核再关中继，端口释放。环境崩了中继跟着回收（`manager.js` 现有 `stopAll` 路径）。

## 3. 失败面（fail-closed）

时序：解析 hop（含校验）→ 逐跳 TCP 连通 → **经整条链**请求探测端点 → 起内核。

| 环节失败 | 返回 | 说明 |
|---|---|---|
| hop 参数非法（type 不认识 / 端口非数字） | `100002` | 建/改环境时就拦（`src/api/contract.js` 的 `ERR.INVALID`） |
| 某一跳连不上 / 认证失败 | `800003`，`reason=proxy_chain_hop_failed`，附 `hop: 1` | **新增 reason 值，code 不变** |
| 链通了但出不了网 | `800003`，`reason=proxy_chain_egress_failed` | 复用现有 egress 判定 |
| 门控 `is_multi_level_proxy="1"` 但环境代理是 `no_proxy` | 不建链，按单跳走 | 对齐对手 `q===noProxy` 分支（`20-` §1.3） |

**不允许**：任一跳失败后退回单跳或直连。对手会静默退回（`20-` §3），我们不退 —— 宁可起不来，不可漏 IP。

## 5. 判据（5 条，可执行）

1. **argv 只 loopback**：`Get-CimInstance Win32_Process -Filter "Name='chrome.exe'" | Select-Object -ExpandProperty CommandLine` 里 `--proxy-server` 只出现 `127.0.0.1:<port>`，不出现 hop1 的 host。
2. **出口是第二跳**：环境内打开 `http://ip-api.com/json/` 回显 IP == hop1 出口 IP，且 ≠ 直连出口。
3. **断链必失败**：把 hop1 端口关掉再 `browser/start` → `code 800003` + `reason=proxy_chain_hop_failed`，且 `Get-Process chrome` 无新增进程。
4. **回收干净**：`browser/stop` 后 `Get-NetTCPConnection -LocalPort <relayPort>` 查不到 LISTEN，无残留 node/chrome 子进程。
5. **凭据不出现**：argv 全文不含密码字符串（取环境 `proxy_config.proxy_password` 的前 6 位做匹配）。

## 6. 不做 / 不兼容项（写进 README）

1. **3 跳及以上**：对手结构上只有 2 跳（`20-` §1.3、§5 收窄），我们不做 N 跳。
2. **`openSystemProxy` / `systemProxyConfig`**：我们没有「系统代理」概念，链的 hop0 恒为本机中继。链形状因此恒为 2 跳（环境代理为空则 1 跳或不建）。
3. **`StaticConfig.ProxyChain`**：不需要（我们用中继），也不回显数组（对齐 `20-` §2「无数组回显」）。
4. **API 新增字段**：零新增。`mutli_level_proxy` 对象只在内部构造，不走 API 入参。
5. **PAC**：保持拒绝（`src/proxy/pac.js:13-19`）。

## 9. 落码后的最终口径（2026-11-12，覆盖上面被推翻的四条）

**链路怎么拼**（`src/proxy/chain.js` 的 `resolveChain`，单点解析）：

| 开关 | 本机系统代理 | 环境代理 | 结果 |
|---|---|---|---|
| `is_multi_level_proxy`（或对手拼写 `mutli_level_proxy`）≠ `"1"` | 任意 | 任意 | 不组链（`mode='off'`），行为与 0.3.2 完全一致 |
| `"1"` | `ProxyEnable=1` 且有可解析 `ProxyServer` | 有 | **两跳**：hop0=系统代理、hop1=环境代理（`mode='chain'`） |
| `"1"` | 未启用（`ProxyEnable=0`） | 有 | **塌成单跳**（`mode='single'`），正常启动，**不是失败** |
| `"1"` | 有 | 无 | 单跳 = 系统代理（`mode='single'`） |
| `"1"` | 无 | 无 | `mode='none'`，与不设代理等价 |
| `"1"` | 系统代理是 PAC（`AutoConfigURL` 非空） | 任意 | 拒绝：`800003` + `pac_unsupported` |

- 读系统代理：`readSystemProxy(overrides?)` 读 `HKCU\Software\Microsoft\Windows\CurrentVersion\Internet Settings` 的 `ProxyEnable` / `ProxyServer`（`host:port` 与 `http=…;https=…` 都解）/ `ProxyOverride`（解出来备查，**不逐请求旁路**）。**可注入**，测试永远不碰注册表。
- 只有 `mode='chain'` 才起中继：只 bind `127.0.0.1`、`listen(0)` 系统分配端口、嵌套 CONNECT、逐跳各带自己的 `Proxy-Authorization`；`stop` 与任何启动失败路径都 close。
- 链式环境下 `Fetch.authRequired` 不启用（Chrome 看到的是无认证回环代理），**单跳仍走它**（回归判据在 `test/proxy-chain.test.mjs` 的 E 组）。
- 系统代理与环境代理是同一个 `host:port` → 去重成单跳（不自连自）。

**失败面（三种，都实测过）**：

| 情形 | 返回 |
|---|---|
| 系统代理未启用 | 正常启动（单跳），**不报错** |
| 某一跳连不上 / 407 / 系统代理只提供 `socks=` 导致两跳组不成 | `800003` + `proxy_chain_hop_failed` / `proxy_chain_invalid`（后者是配置不可用），**零内核进程** |
| 系统代理是 PAC | `800003` + `pac_unsupported` |

`failed_hop` 下标口径：407 → **当前这一跳**（`via`）；其它非 200 → **下一跳**（当前跳连不上它）；最后一跳请求目标失败 → 最后一跳。`lastError` 由中继记录，预检失败时读出来塞进错误对象。

**判据（已落码，两个文件）**：

```
node --no-warnings test/chain-rules.test.mjs   → 31 passed, 0 failed
node --no-warnings test/proxy-chain.test.mjs   → 37 passed, 0 failed
```

`test/proxy-chain.test.mjs` 的件与断言：假系统代理（记录型 hop0）+ 假环境代理（记录型 hop1，可要求 Basic 认证）+ 目标 server（`target.test:<port>`，代理侧解析到 127.0.0.1，绕开 loopback 隐含 bypass 的干扰）。A：两跳都有命中、hop0 上游 = hop1、hop1 的 client 源端口 = hop0 出站 socket 本地端口、argv 只有本地中继、stop 后端口不可连；B：无系统代理 → hop0 命中 0 而 hop1 有命中、不起中继；C：hop1 不可达 → `failed_hop=1` + 零内核 + 目标命中 0；C2：系统代理要认证 → `failed_hop=0` + 零内核；D：运行中关 hop0 → 请求失败且目标命中不增加（防回落直连）；E：单跳认证仍走 `Fetch.authRequired`。每条「0 命中」都成对给正例。

**明确不做（backlog，别当已实现）**：系统代理需要认证（注册表无凭据，直接 fail-closed）、`ProxyOverride` 逐请求旁路（旁路=直连，与 fail-closed 冲突）、两个远端代理串起来（我们的扩展、非对手口径）、https/socks 跳进链、PAC。
