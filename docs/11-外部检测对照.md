# 外部检测站对照（P7 之后 · 第一轮）

> ⚠️ 本文是一次**外部**检测的实测记录，不是自检。自检 19 项只证明「我们注入的东西自己一致」，
> 不证明「检测方看不出来」。这一页是第一次拿第三方检测站当裁判。
> 数字会随内核版本变化，引用前先看文末的复跑命令与内核版本。

## 1. 为什么要做这个

在这轮之前，我们对「能不能过检测」的全部证据都是自证的：

- 五处 canvas 哈希一致 → 只证明噪声同源，不证明被识破；
- 自检 19 项 pass 10 / warn 9 / fail 0 → 只证明我们自己设计的检查项都过了；
- `native()` 把注入函数伪装成 `[native code]` → 只证明我们**希望**它看起来像原生的。

把 `navigator.hardwareConcurrency` 从 32 改成 6，从来没有人从**外部**看过这改动会留下什么痕迹。所以第一份外部证据必须补齐。

## 2. 方法：两遍相减

关键设计是**基线**。同一台机器、同一个 Chrome 二进制（157.0.8103.40）、同一套启动参数（走产品自己的 `buildArgs`），跑两遍 creepjs：

| 模式 | 怎么起 | 差别 |
|---|---|---|
| `plain` | 直接调 `launchChrome` + 自己连 CDP | **不调 `injectAndOpen`**，即零注入 |
| `ours` | 走 `startProfile` | 注入全开（10 项） |

两次结果相减，才能分清「我们改出来的问题」和「这台机器本来就有的问题」。
只跑 `ours` 是没意义的 —— 25% 的 like headless 里有多少是我们的、有多少是本来就有的，单跑看不出来。

工具：`tools/detector-compare.mjs`，一次跑完两遍并直接打印对照表。

## 4. 已定（这次能下结论的）

1. **注入让「像 headless」的程度涨了 13 个百分点（25% → 38%）。** 裸 Chrome 在这台机器上是 25%，我们一注入变成 38% —— 这是我们自己造的痕迹，不是环境。已作为 P8-C 交给复刻手：必须压到 ≤ plain，且要给出「是哪几项被判」的逐项 diff，不许猜。
2. **`deviceMemory` 与 `jsHeapSizeLimit` 互相矛盾。** 我们报 8GB，堆上限却是 4.09GB 那一档，且这个值两边完全一样（说明它跟真实内存走、我们没碰）。creepjs 把两个数并排显示，检测方不用算就能看出矛盾。已作为 P8-D。
3. **字体与语音的中文泄漏不是我们造成的。** `platform hints` 和 `speechSynthesis` 第一条声音（`Microsoft Huihui – zh-CN`）在 plain 和 ours 完全一致 —— 是这台中文 Windows 的固有泄漏。这意味着「在国内机器上伪装 en-US 环境」目前会被这两项一眼看穿，属跨机一致性的硬伤，但**与注入实现无关**，留给字体/语音那一轮。

## 5. 未定（还下不了结论的）

- **38% 里究竟是哪几项？** 我只拿到总分，还没做 `window.Creep` 的逐项 diff。在做完之前，任何「已经修好了」的说法都不成立。→ **已答，见第 7 节。**
- **0% headless / 0% stealth 是不是假阴性？** creepjs 这两栏在 plain 和 ours 都是 0%，连同 `chromium: true` 一起看，更像它在这台机器上根本没测到那类特征，而不是「我们干净」。不要拿这两栏当卖点。
- **WebRTC 那栏在 ours 显示 `blocked`**：这次没绑代理，`blocked` 与「没配代理」一致；绑了真代理之后应该变成真实出口 IP，那一轮才能验 WebRTC 泄漏面（需要真代理，当前没有）。
- **只测了一个检测站。** creepjs 一个站点的结论不能外推到 browserleaks / pixelscan / iphey。要不要加第二个站，等 C 这轮做完再定。

## 7. 第二轮（P8-C / P8-D 修完，2026-11-11 17:38）

### 7.1 先定位：38% 是哪两条抬起来的

creepjs 把 like-headless 的 16 个标志位渲染在 DOM 里（`Like Headless` 那一块），
直接抠出来做 plain vs ours 的逐项 diff —— **16 项里只有两条不同**：

| 标志位 | plain（裸 Chrome） | ours（修复前） |
|---|---|---|
| `noTaskbar` | false | **true** |
| `hasVvpScreenRes` | false | **true** |
| 其余 14 项 | 一致 | 一致 |

两条都出在屏幕/窗口，跟注入脚本本身无关：

- `noTaskbar`：creepjs 判的是 `screen.height === screen.availHeight && screen.width === screen.availWidth`。
  我们用 `Emulation.setDeviceMetricsOverride` 只设了 screen 尺寸，`avail*` 被撑成和它一样 →「没有任务栏」。
  裸 Chrome 在这台机器上是 1440 / 1392（差的 48 就是任务栏）。
- `hasVvpScreenRes`：判的是 `innerWidth === screen.width && outerHeight === screen.height`（或 visualViewport 同）。
  我们原来 `--window-size` 和 Emulation 视口都按屏幕尺寸拉满，正好命中 —— 而「窗口等于屏幕」正是 headless 的默认形态。

2 / 16 = 12.5 个百分点，与实测的 13pp 对得上。

### 7.2 修法与复跑

- `src/fingerprint/view.js`：新增 `windowSizeFor(screen)`，窗口默认比屏幕小一圈（屏幕分辨率仍是配置值）。
- `src/kernel/chrome.js`：`--window-size` 用上面的窗口尺寸，不再等于屏幕。
- `src/runtime/manager.js`：`Emulation.setDeviceMetricsOverride` 的视口用窗口尺寸，`screenWidth/screenHeight` 仍是屏幕。
- `src/kernel/inject.js`：按视图里的 `avail_width/avail_height` 覆盖 `Screen.prototype.availWidth/availHeight`（留出 40px 任务栏）。

| 项 | plain | ours（修复后） |
|---|---|---|
| **like headless** | 25% | **25%（差 0pp）** |
| `noTaskbar` / `hasVvpScreenRes` | false / false | false / false |
| screen | 3440x1440 | 1536x864 |
| deviceMemory | 32 | **32**（P8-D：取真实内存档位） |
| jsHeapSizeLimit | 4,395,630,592 | 4,395,630,592 |
| hardwareConcurrency | 32 | 6（我们改的，属设计内） |

P8-D 的做法：`device_memory` 默认取真实内存档位（这台 96G → 2 的幂封顶 32，与裸 Chrome 一致），
值域从拆解表的 2/4/6/8 扩到 16/32（Chrome 157 实测会返回 32，旧域是 deviceMemory 上限 8G 那个年代的）。
单环境仍可显式改这个字段。

### 7.3 这一轮不能吹的地方

- **25% 只是「不比裸 Chrome 更像 headless」，不是「过了检测站」。** creepjs 在这台机器上对裸 Chrome 也给 25%。
- `chromium: true` 两边都是 true：这台机器跑的就是 Chrome，这栏本来就是我们暴露的。
- 字体 / 语音的中文泄漏原样存在（`Microsoft YaHei UI` / `Microsoft Huihui`），plain 与 ours 一致，属机器，不属注入。
- 只测了 creepjs 一个站。别的站（browserleaks / pixelscan / iphey）还没看。

## 8. 第三轮（P9-C / P9-A 之后，2026-11-11 19:32）

这一轮换了起点：**先由逆向的人用自己的探针当裁判**，他指出 MediaDevices 被判成 `synthetic`，三条都能被页面直接抓到 ——
跨 origin `deviceId` 恒定、未授权就返回非空 label、报得出摄像头但 `getUserMedia({video:true})` 抛 `NotFoundError`。

### 8.1 改法（P9-C）

- 放弃「整份伪造设备列表」，改成**真实 `enumerateDevices()` + 只改 label**：
  未授权原样返回（label 天然空串）；授权后按 kind 的第 i 个设备改名，`deviceId` / `groupId` / `kind` 不动。
- `deviceId` 不再自己派生 —— Chrome 原生就是**按 origin 加盐**的，保留原生即自动满足「跨 origin 不同、同 origin 刷新不变」。
- 枚举里没有摄像头就不报摄像头，`getUserMedia({video:true})` 与枚举自然一致。
- 依据：**「造一整套假设备」不如「给真实设备改名」隐蔽**（AdsPower 走的也是这条路）。

### 8.2 改法（P9-A 语音）

- `SpeechSynthesis.prototype.getVoices` 只保留环境语言（含同语种变体）的声音，其余丢弃；
  返回的仍是原生 voice 对象，只覆盖 `default`（保证恰好一条），`speak` / `cancel` / `SpeechSynthesisUtterance` 一字不碰。
- 宿主没有该语言声音时**保持原生、不造**（本机缺 `vi-VN` / `th-TH`）。

### 8.3 复跑数字（`tools/detector-compare.mjs`，同一台机器、同内核 `157.0.8103.40`）

| 项 | plain（零注入基线） | ours（P9 之后） |
|---|---|---|
| **like headless** | 25% | **25%（差 0pp，没被抬回去）** |
| `headless` / `stealth` | 0% / 0% | 0% / 0% |
| **语音数量** | **25**（首条 `Microsoft Huihui - Chinese (Simplified, PRC)` / zh-CN） | **6**（首条 `Microsoft Mark - English (United States)` / en-US） |
| `deviceMemory` | 32 | 32 |
| `jsHeapSizeLimit` | 4,395,630,592 | 4,395,630,592 |
| `platform hints` | `Arial,"Microsoft YaHei UI"` | `Arial,"Microsoft YaHei UI"`（字体，P9-B 只标注不注入） |
| `hardwareConcurrency` | 32 | 16（环境配置，属设计内） |

媒体设备的真机证据不在 creepjs 里，走独立脚本（`npm run test:media-speech`，16/16）：
未授权 `{audioinput:1, videoinput:0, audiooutput:1}`、id/label 全空；授权后 3 麦 5 喇叭、label 来自命名池且同类内不重复、
跨 origin `deviceId` 不同、`getUserMedia({video:true})` = `NotFoundError`、`track.label` 与枚举同名。

### 8.4 这一轮仍然不能吹的地方

- **25% 依旧是「不比裸 Chrome 更像 headless」**，不是「过了检测站」。
- **字体枚举面仍是机器属性**（`Microsoft YaHei UI` 等），P9-B 的结论是**不写 JS 注入**：根治要自编译 Chromium，JS 层投影只会造出新的不一致。标 `none` 不等于字体指纹裸奔（canvas 文本噪声已覆盖字形渲染），裸的是「宿主装了哪些字体」这个枚举面。
- 语音只证明「列表变了」：宿主中文声音被挡掉、形状完整、`speak` 不受影响；**没有验证发音是否真的是该语言**（宿主缺 `vi-VN` / `th-TH` 时我们保持原生）。
- 媒体设备只保证「与真实枚举一致」，**不保证设备名在别的机器上看起来合理** —— 命名池是固定的一小组 Windows 常见设备名，跨机一致性靠它，不靠宿主。
